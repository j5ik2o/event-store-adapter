# Separate the aggregate head from the snapshot and make it the unit of the change feed

> The choice of keys (the decision to align them with logical shards) and the recording and checking of the shard count and hash method were withdrawn in [ADR-0006](0006-key-by-aggregate-id-instead-of-logical-shards.md) (2026-10-03). The aid string is now used as the key. The statements about keys below are a record of the decision and comparison at that time. The decision to separate the head itself does not change.

DynamoDB Streams guarantees order only among changes to the same item. Because the journal has one item per event, the journal's Streams does not guarantee order even for events of the same aggregate ([modern-ddd-book#91](https://github.com/j5ik2o/modern-ddd-book/issues/91)). If events are carried on an item that is updated every time for each aggregate, that item's Streams becomes a change feed in order, per aggregate.

The problem is that this "item updated every time" is, at present, the snapshot's current item. The current item already doubles in two roles: the check point for optimistic locking, which advances version on every append, and the cache of aggregate state, which is written only occasionally. If carrying the change feed is also placed on it, the meaning of the snapshot breaks for DynamoDB's convenience.

So we make the check-point role an independent concept, the **aggregate head**. The core contract defines it as follows. There is one aggregate head per aggregate, and it advances in the same atomic write as the append (the meaning of "atomic write" was redefined in ADR-0005 as an observable confirmation), and it holds version, the latest seq_nr, and the event envelope appended by that write. The snapshot returns to being a pure state cache and may be older than the head. The change feed is defined as the sequence of head transitions. This definition contains no DynamoDB-specific terms. The part "Streams guarantees order only per item, so make the head an independent item and carry the events on it" is written only in the DynamoDB storage profile.

In the DynamoDB profile, the aggregate head is made an independent item in a dedicated table, and Streams is enabled only on this table. At that time, we aligned the keys with the same logical-shard approach as the journal, with the partition key `${型名}-${シャード番号}` (type name and shard number) and the sort key `${型名}-${値}` (type name and value). We also adopted a policy of treating the shard count as immutable and checking the shard count and hash method recorded in the table when the store is created. This policy on keys and configuration checks has been withdrawn in ADR-0006.

## Considered Options

For the comparison of write capacity, we use an example of a 20KB snapshot, 0.5KB events, and a snapshot saved every 10 events. DynamoDB rounds up the write item size in units of 1KB, and a transaction consumes twice as much. Even when UpdateItem changes only some attributes, it is charged for the whole item, the larger of before and after the update ([Developer Guide: read and write operations](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html)).

- **A. Put the events together in the current item (the original proposal in #91)**: The change is the smallest. However, even an append of events alone updates a 21KB item including the snapshot, so each append costs about 44 WCU (about 440 WCU for 10 events). This is the same in rs v3's current state; placing version in the current item is already a cost. The whole snapshot is also carried in Streams' NEW_IMAGE every time, and the 400KB limit is shared between the snapshot and the events. We do not adopt it.
- **B. Make the aggregate head an independent item in a dedicated table (adopted)**: An append of events alone costs about 4 WCU (1KB for the journal and 1KB for the head), and when a snapshot is saved, about 42 WCU more is added (about 80 WCU for 10 events). The stream records are small, and only head transitions flow through Streams. In exchange, there are three tables, and the transaction when saving a snapshot involves three items.
- **C. Put the head in the journal table**: The number of tables does not increase. However, unordered event items and ordered head items would mix in the journal's Streams, and attribute names would have to be chosen so that the head does not get mixed into the aid / seq_nr GSI either. We do not adopt it.
- **D. Use the journal's Streams as a notification, and have the subscriber check seq_nr and reorder (the current method in modern-ddd-book ch10)**: No change to the library is needed. However, each subscriber needs its own checking and compensation logic, and the compensation relies on eventually consistent GSI reads. We do not adopt it as a guarantee of the library, and keep it as a safety net on the subscriber side.

For the head's key, we compared the following two options at that time.

- **Use aggregate_id as the partition key as it is (not adopted at that time; adopted in ADR-0006)**: The head's position does not depend on the hash function or the shard count, so it is safe by construction. However, it would split the journal from the logical-shard approach and depart from the design principle shared by event-store-adapter and pekko-persistence-dynamodb, so we did not adopt it at that time.
- **Align with the logical-shard key (adopted at that time; withdrawn in ADR-0006)**: The design principle stays consistent. In exchange, if any of a change in the shard count, a discrepancy in the settings between implementations, or an error in the hash implementation occurs, the existing head is lost. If the head is lost, the aggregate is judged not to exist, a new creation goes through at a different position, and an event with seq_nr=1 is written twice. So at that time we decided to close this path by treating the shard count as immutable, checking the settings when the store is created, and verifying the hash implementation with the conformance test data.

Write distribution is sufficient with either option. Even with a logical-shard key, writes to the head are distributed as much as the journal. A transaction can write items in different tables and with different keys together, so the choice of keys does not affect whether the transaction holds either.

## Consequences

- At that time, a setting that records the shard count and hash method, and a check at creation, were needed. This was because rs v3 also reads the current item directly by pkey, to prevent double creation caused by a change in the shard count. Because logical shards were dropped in ADR-0006, this recording and checking is no longer a current requirement.
- Because the snapshot became a pure cache, we decided it may be absent (agreed on 2026-10-02, core contract R-3). New creation can also be done without a snapshot, and when there is none, replay starts from the beginning of the journal.
- Reading the latest snapshot involves two items, the head and the snapshot. With BatchGetItem's strongly consistent read, it can be done in one round trip. Reading the two items is not atomic, but if an old version is read it is detected by the optimistic lock of the next write, so it errs on the safe side.
- Because the head holds the latest seq_nr, `event.seq_nr == head.seq_nr + 1` is enforced by a condition expression at write time (agreed on 2026-10-02, core contract W-8). rs v3 explicitly stated that "the library does not verify continuity," so this is a change of policy. Gaps no longer occur in the change feed, and gap detection on the subscriber side becomes strict.
- Because continuity is enforced and only one event is appended per write, version and seq_nr always match. So version is abolished, and the optimistic lock is checked against the head's seq_nr (ADR-0004). Wherever this ADR's body says version, read it as seq_nr from ADR-0004 onward.
- Subscribers of the change feed are required to provide idempotency and gap detection on any transfer path. DynamoDB Streams guarantees per-item order and that each record appears once, but retention is 24 hours. Through Kinesis Data Streams, reordering and duplicates can occur. A subscriber discards duplicates by (aggregate_id, seq_nr), and when it finds a gap, it fills it from the journal. modern-ddd-book ch10's `applyInOrder` remains as this safety net, not as the everyday path.
- rs becomes a breaking change equivalent to v4 (adding tables, changing the read and write paths). Migration of existing rs v3 data is done by scanning the whole table, enumerating the old items, and rewriting them in the new format. The method of recomputing the old pkey is avoided, because there is no guarantee that `DefaultHasher` of the toolchain at that time is the same as at write time.
- Realization in Pekko (pekko-persistence-dynamodb) is outside the scope of this repository and is handled on the modern-ddd-book#91 side.
