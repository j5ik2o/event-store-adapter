# Conformance test data v1

## About this guide

This guide is the English translation of the developer-facing explanation in [`conformance/README.md`](../conformance/README.md). Its Japanese counterpart is [conformance-guide.ja.md](conformance-guide.ja.md).

- `conformance/README.md` is part of the distributed data, pinned to the version of the distribution (`1.3.0`). Its SHA-256 is listed in `conformance/manifest.json`. The Japanese README is kept as it is and is not changed or translated.
- The normative documents are those under [`docs/spec/`](spec/README.md). The data adds no rules.
- [`conformance/COVERAGE.md`](../conformance/COVERAGE.md) is the coverage table. It is generated fixed data (generated by `validate.py --update-coverage`), so refer to it and do not edit it by hand.
- Paths in the tables below (such as `values/` and `scenarios/core/`) are relative to `conformance/`.
- The rule definition lines in the specification can be written in two forms: the Japanese classification (必須・推奨・任意) and the English MUST / SHOULD / MAY. See "Versions, hashes, and distribution" below.

## Overview

This is data that distributes the expected values of the core contract, the DynamoDB profile, the memory profile, the SQLite profile, the Spanner profile, and the Bigtable profile as language-independent UTF-8 JSON. The version of the data is `1.3.0`. The [core contract](spec/core-contract.md), the [DynamoDB profile](spec/storage/dynamodb.md), the [memory profile](spec/storage/memory.md), the [SQLite profile](spec/storage/sqlite.md), the [Spanner profile](spec/storage/spanner.md), and the [Bigtable profile](spec/storage/bigtable.md) are normative, and this data adds no rules. It also includes the 4 FNV-1a 64 entries that the [hash specification](spec/storage/hash.md) requires to be included, and the value table of the fixed binary format of the Bigtable envelope (BT-D6a). It has 169 cases in total: 40 values, 128 operation scenarios (42 common, 45 DynamoDB-specific, 7 memory-specific, 7 SQLite-specific, 14 Spanner-specific, 12 Bigtable-specific, and 1 shared scenario common to SQLite, Spanner, and Bigtable), and 1 layout, covering 75 rules. Of the 124 rules defined by the 7 specification documents, every one has either a case or a reason for exclusion in `coverage.json`. The common scenarios cover the 5 storage backends `memory`, `dynamodb`, `sqlite`, `spanner`, and `bigtable`. This verification covers only the data and the tools, and is not run against language implementations or storage backends.

The Schemas are draft 2020-12. The common definitions are in `schema/common.schema.json`. `$id` is an identifier, and the validation tool registers the Schemas in the same directory and resolves references offline. There is no need to access this URL.

JSON string values and attribute names are part of the data and are not rewritten according to each language's conventions.

## How to read the value tables

`operation` means the following checks. It does not require a function of the same name in the public API; the runner maps it to the checks at construction and before writing.

| Operation | Input | Expected on success |
|:--|:--|:--|
| `buildAid` | `aggregate_id.type_name` and `value` | The aid string of `expect.value` |
| `validateOccurredAt` | `iso8601`, `epoch_nanoseconds` from the epoch, and `event_seq_nr` for error descriptions | Equivalence with the input converted to the standard time type |
| `validateSeqNr` | `seq_nr` and `context` | The integer of `expect.value` |
| `fnv1a64` | A `utf8` string | The fixed 16-digit hexadecimal of `expect.value` (with `0x`) |
| `encodeBigtableEventEnvelope` | `aid`, `seq_nr`, `occurred_at_ns` (decimal string), `manifest`, `payload_hex` (lowercase hexadecimal) | The envelope's lowercase hexadecimal of `expect.value` (BT-D6a) |
| `encodeBigtableSnapshotEnvelope` | `seq_nr`, `manifest`, `payload_hex` | The envelope's lowercase hexadecimal of `expect.value` (BT-D6a) |
| `decodeBigtableEnvelope` | `kind` (`event` or `snapshot`) and `bytes_hex` | Decoding a malformed envelope gives `error.category = storage` |

`user_string` of `buildAid` is an alternative representation returned by the user's `Display` and the like. The runner prepares a test implementation of an ID that uses this string, and confirms that the library assembles the aid from the type name and the value. T-12 is judged by the UTF-8 byte count of the type name, value, and separator all together. The multibyte cases are meant to detect implementations that judge by the character count.

`context = value` of `validateSeqNr` is the general range of T-9, and 0 is also valid. `context = event` is application to an event, and makes 0 a contract violation of W-6. It is not required to save the upper-limit value as a first append. This is a separate case from the continuity check by W-8. Anything outside T-9's range is treated as a contract violation. The statement of T-9 in the list in chapter 4 of the core contract will be done separately by the coordinator, following the agreement of 2026-10-05.

`validateOccurredAt` is run on an aggregate whose type name is `ConformanceTime` and whose value is the case ID. First, numbers 1 through `event_seq_nr - 1` are confirmed in order at the time `1970-01-01T00:00:00.123000000Z`. Then the event number `event_seq_nr`, which has the input time, is written with `persistEvent`. The payload is an empty object and the manifest is an empty string. A success case reads number 1 back and compares the time. An out-of-range case compares the contract violation at number 7, so it does not overlap with a violation for a skipped number, and the 7 in the message is not accidentally satisfied by T-13's number. `validateSeqNr` uses the construction of the envelope or the library's range-check hook, and must not be a check in which the runner merely computes the same formula.

`fnv1a64` maps to the shared hash implementation of profiles that use a hash. The 4 inputs are the table in hash.md itself, with no construction or validation of aid in between. The output is compared as an unsigned 64-bit value. The fixed 16-digit notation is for comparison and does not require the format of keys in the storage. DynamoDB does not use this hash for storage keys. Spanner and Bigtable use this hash for keys, but embedding it into the key depends on the form of the raw row, so it is not included in the data and is left to each language's tests (K-2).

`encodeBigtableEventEnvelope` and `encodeBigtableSnapshotEnvelope` verify the fixed binary format of the Bigtable envelope (chapter 4 of the [Bigtable profile](spec/storage/bigtable.md), BT-D6a). The runner calls the library function that assembles an envelope from the input items, and confirms that the returned byte sequence matches `expect.value`. It then decodes the expected byte sequence and also confirms that it matches the input items. `payload_hex` is the payload's byte sequence, the serializer's output itself. The lengths of `aid` and `manifest` are counted in UTF-8 bytes. `occurred_at_ns` is signed 64-bit, and `seq_nr` is unsigned 64-bit, in big-endian. `decodeBigtableEnvelope` represents an envelope for which decoding `bytes_hex` gives a storage error (unused trailing bytes, a length mismatch, an unknown format version number). If a correct envelope is placed in this operation, it is rejected as an error in the data. The verification tool, in `tools/conformance/data.py`, has encoding and decoding independent of the specification and checks the expected values of the table.

### Representational capability of time and numbers

Epoch nanoseconds are written as decimal strings so that no precision is lost in JSON number parsers even at and beyond the edges of signed 64-bit. Calculation is done with integers and does not pass through floating point. In the envelopes of operations, `occurred_at` is a UTC ISO 8601 string with 9 decimal digits of fractional seconds.

On success with `expect.precision_policy = native-time-type`, the runner converts the input to the language's standard time type and uses that value as the expected value. T-3 is checked by the equivalence of the converted input and the read value. The direction of rounding is not fixed. The epoch nanoseconds of `expect.value` are a reference value before rounding, and an exact match is not required as is for a type of lower precision. The runner reports the converted value and the actual value. This does not mean that it may be replaced by the store's current time.

The same policy is applied to event.occurred_at in operation scenarios. The expected time of a returned envelope is the fixture value converted to the standard time type at write time.

A case with `representation.time_precision` is a boundary case by precision. An implementation whose standard time type can represent nanoseconds runs the `nanoseconds` case, and one limited to milliseconds runs the `milliseconds` case. The millisecond case has the outermost millisecond within the range and the nearest millisecond outside the range. The expected value of one boundary must not be applied by rounding the other boundary. Time cases without a precision marker are run by all implementations using the value converted with the standard time type. If an implementation using a standard time type that can represent only seconds or microseconds is added, boundary data must be added.

The runner first reads `seq_nr` values such as -1 and 2^53 (9007199254740992) as generic JSON values or arbitrary-precision integers. If the data is decoded directly into the target API's unsigned or fixed-width type, the input is lost before it reaches the library's check. After preserving the exact value, attempt the conversion to the API.

Cases with `representation.signed_seq_nr = true` are run only by implementations that can represent negative numbers in the argument type. An implementation that uses unsigned types reports them as "not representable". A case that does not satisfy the boundary or sign condition must not be treated as a success.

## How to read the operation scenarios

Each scenario is run on an independent store. When a second store is needed within a scenario, it is created with the `createStore` operation (see "Second store and rewriting of payloads (memory)"). DynamoDB table names and GSI names are assigned by the runner, and the 3 tables of the same scenario are placed in the same region. Items of other cases are not reused. The runner prepares hooks for deterministically running the declared retention process, and hooks for inspecting internal history, failure notifications, and SDK requests.

1. Confirm that the storage to run is in `backends`. `requires = ["ttl"]` requires the TTL method. Scenarios that observe TTL marking cover only DynamoDB. Spanner's TTL-method marker time is the server's `CURRENT_TIMESTAMP()`, a clock cannot be injected, and the expiry cannot be observed deterministically, so it is not included in the scenarios (SPN-12).
2. Create the store with the `store` settings. `retention_count = null` does not create history and stores only the current one. `delete` deletes old history, and `ttl` marks it. `ttl_grace_seconds` is DynamoDB's grace period in seconds. `change_feed = true` is a setting that requests the provision of a change feed, and when omitted it is not requested. `lock_wait_milliseconds` specifies SQLite's lock wait (the busy wait time of SQ-1) in milliseconds, and can be placed in scenarios whose `backends` is only `["sqlite"]`. A scenario that keeps holding the write lock explicitly specifies a short value. `transaction_retry_limit` is the limit on retries after Spanner aborts (ABORTED), not counting the first attempt (it can be placed in scenarios whose `backends` is only `["spanner"]`). `ttl_grace_days` is the number of days of Spanner's TTL grace, separate from `ttl_grace_seconds` (it can be placed in scenarios whose `backends` is only `["spanner"]`. It must be specified in Spanner scenarios with `retention_mode = ttl`). `envelope_limit_bytes` is the number of bytes of Bigtable's envelope limit, with a default of 1048576 when omitted (it can be placed in scenarios whose `backends` is only `["bigtable"]`). The names are common names in the data, and are mapped to the implementation's configuration API.
3. If there is `seed.items`, put those items in with test privileges before the store is created. The types of values and the handling of binaries are the same as in the attribute inspection described later. If the configuration item is not in the seed, initialize by the normal creation procedure. If there is `seed.configuration`, record, before the store is created, the configuration that the previous initialization recorded in the storage, written with the profile's config item names. SQLite's item names are `store_id` (a lowercase UUID), `layout_version`, `keep_snapshot_count` (null or a positive integer), `retention_mode`, and `change_feed_enabled` (0 or 1). Spanner's item names are SQLite's items plus `ttl_grace_days` (a positive number of days only for ttl, null otherwise), and `change_feed_enabled` is a boolean. Spanner's `seed` must always write, alongside `configuration`, the number of days of the row deletion policy of snapshot_history as `row_deletion_policy_days` (the number of days, or null if there is no policy). Bigtable's `seed.configuration` writes the configurations of the two tables `journal` and `head` separately. The item names of each table are `store_id`, `layout_version`, `keep_snapshot_count` (null or a positive integer), `retention_mode` (`delete`), and `envelope_limit_bytes`. The runner records this through the storage's normal initialization path or with test privileges. It does not write raw rows or the shape of the SDK, and cannot be placed in the same scenario as `seed.items`. A scenario that uses `seed.configuration` observes the result of creation (`initialization`).
4. If there is `initialization`, check the creation result. A case of creation failure has no operation sequence. Failures before creation are registered first.
5. If there is `generators`, expand the strings by the procedure described later. Read `fixtures.events` and `fixtures.snapshots`, and construct the envelopes referenced just before each operation. The keys are reference names valid only within the scenario. When the manifest is omitted, the expected value is an empty string. A rule violation that arises during the construction of an envelope with invalid input is also caught as a failure of the corresponding operation. The runner's own pre-checks must not substitute for the library's checks.
6. Run `steps` in array order, without running them concurrently. The arguments `event` and `snapshot` are references to fixtures, and `aggregate_id` and `seq_nr` are values. A write appends one event per operation.
7. Check each operation's `expect` and the `observe` specified for that operation. In scenarios with retention failures or delays, observe after the declared retention and inspection hooks have completed. Hooks must not change the success or failure of writes.

The scenarios of `memory/configuration.json` expect that settings requesting the expiry method (`retention_mode = ttl`) and the change feed (`change_feed = true`), which the memory storage does not provide, fail at creation with the `configuration` category. An implementation whose language's configuration API cannot represent the request itself (for example, the configuration type has no field for the expiry method or the change feed) may report it as "not representable" with a reason. The handling is the same as for `signed_seq_nr`. If the request can be represented but does not become a configuration error, it is a failure.

`sqlite-ttl-unsupported` (SQ-11) and `sqlite-change-feed-unsupported` (SQ-20) in `sqlite/configuration.json` also expect that settings requesting the expiry method and the change feed, which the SQLite storage does not provide, fail at creation with the `configuration` category. The handling of "not representable" is the same as above. This handling applies only to cases of settings requesting capabilities that are not provided (the 2 cases above and the 3 cases in the next paragraph), and is not extended to the mismatch scenarios that use `seed.configuration` (where the recorded retention count, layout version, or `change_feed_enabled` differs from the settings). The mismatch scenarios can represent the request, so it is a failure unless creation fails with the `configuration` category. A matching scenario succeeds in creation.

`spanner-change-feed-unsupported` (SPN-17) in `spanner/configuration.json`, and `bigtable-ttl-unsupported` (BT-13) and `bigtable-change-feed-unsupported` (BT-17) in `bigtable/configuration.json`, also expect that settings requesting capabilities the storage does not provide fail at creation with the `configuration` category. Spanner provides the expiry method, so the expiry-method setting is not treated as a lack of capability. The handling of "not representable" is the same as above.

Spanner scenarios that use `seed.configuration` expect creation to fail with the `configuration` category when the layout version, retention count, or retention method mismatch (SPN-2), when the number of TTL grace days does not match among the client, the recorded configuration, and the row deletion policy (SPN-16), and when the recorded `change_feed_enabled` is true (SPN-17). A scenario where the client's number of grace days is 0 or less expects the same category without seeding (SPN-16). Bigtable scenarios that use `seed.configuration` expect creation to fail with the `configuration` category in these cases: a mismatch between the configurations of journal and head (the check in chapter 2. The decision number BT-D1 is not a coverage target, so in the data the rule of the mismatching item is attached. `bigtable-seeded-table-envelope-limit-mismatch` has a mismatching envelope limit, so it gets BT-16), a mismatch of the retention count with the client (chapter 2. There is no BT numbered rule, so E-1 is attached as in DynamoDB's configuration error scenarios), and a mismatch of the envelope limit with the client (BT-16). A setting whose envelope limit exceeds the maximum (8388608) and a setting in which not even the smallest envelope fits (16) also make creation fail with the `configuration` category (BT-16). In every matching scenario, creation succeeds.

### Second store and rewriting of payloads (memory), and shared stores (SQLite, Spanner, Bigtable)

The scenarios of `memory/stores.json` (MEM-2) and `memory/payload-isolation.json` (MEM-6) use the following operations. In both, `backends` is only `["memory"]`, and `rules` has MEM-2 or MEM-6. The scenarios of `scenarios/stores/shared.json` use only `storage = shared` of `createStore`, and `store`; `backends` is only SQLite, Spanner, and Bigtable (`sqlite`, `spanner`, `bigtable`), and `rules` are core contract numbers (W-7, W-8, and so on). What is shared is the same file in SQLite, the same database and the same prefix in Spanner, and the same instance and the same tables in Bigtable. In the shared second store, the aggregate written by the first store can be read, and appending an old seq_nr or a duplicate seq_nr results in an optimistic lock. `storage = new` can be used only in memory scenarios. Using it in SQLite, Spanner, or Bigtable scenarios is rejected as an error in the data.

- **First store**: The reserved name is `primary`. An operation that omits `store` is an operation on `primary`, and the meaning of existing scenarios does not change.
- **`createStore`**: Creates a second store in the middle of a scenario. `arguments.name` is the reference name of the new store, and `primary` and names already created cannot be used. If `arguments.storage` is `new`, an empty independent store is created as a new storage. If `shared`, it is created by explicitly sharing the storage of the already created store that `arguments.shared_with` points to, sharing all records, settings, and exclusive control. When creating with `shared`, in memory, the runner does not pass the settings separately to the second store, and makes the shared instance use the settings held by the storage (the first store's `store`) (MEM-D11). Creating the second store with the same settings passed would not confirm the sharing of settings. In SQLite, Spanner, and Bigtable, the settings recorded in the storage are checked against the client's settings, so the runner passes the same settings as the scenario's `store`. `memory-store-shared-configuration` confirms that the shared store also shares the retained history count, using the history after repeated appends with snapshots. The expectation is only `result = success`.
- **`store`**: Optionally held by persistence and read operations. It is the reference name of an already created store, and indicates the store on which the operation is run. A reference name before creation cannot be used.
- An independent scenario writes to another store before `createStore`, and reads the same aggregate from the newly created store. This read returns "none" or an empty sequence. A scenario that only reads the second store without writing anything would be a vacuous success, so it is rejected as an error in the data.
- An implementation whose language API can create a storage with a name confirms that a second storage given just the same name has the same result as the independent scenario (records are not shared). An implementation that has no API for naming need not confirm this point.

`mutateWrittenPayload` rewrites the payload of the event written, for a successful earlier write that `arguments.operation` points to, while keeping the same object that the runner holds locally. `mutateReadPayload` rewrites, in the same way, the payload of the event `arguments.event`, among the results obtained by the earlier `getEventsByIdSinceSeqNr` that `arguments.operation` points to. Both replace the position pointed to by `arguments.pointer` (an RFC 6901 JSON Pointer) with `arguments.value`. The root of the pointer is the payload of the written event, and an empty pointer cannot be used. The expectation is only `result = success`, and when read again after the rewrite, the value written before the rewrite is returned.

A scenario in which the rewrite position does not exist in the written payload, and a scenario in which the value after rewriting is the same as the current value, would be vacuous successes, so they are rejected as errors in the data.

An implementation whose language types or API cannot represent this rewriting itself (the value is passed with ownership and cannot be touched after writing, the payload type cannot be rewritten, and so on) may report the corresponding cases of `memory/payload-isolation.json` as "not representable" with a reason. The handling is the same as for `signed_seq_nr`. This handling applies only to the 2 cases of `memory/payload-isolation.json`, and is not extended to other cases. If the rewrite can be represented but the stored value changes, it is a failure.

`store.retry_limit` is the upper limit on the number of re-requests of the configuration check, not counting the first request. If the implementation's limit is not a count but a wait time, the runner reproduces reaching the limit with the same sequence of unprocessed responses. Tests that wait for exponential backoff may shorten real time with a clock hook that observes the request sequence and the wait time.

### Operations that keep holding the write lock (SQLite)

`holdWriteLock` and `releaseWriteLock` are used only by the scenarios of `sqlite/write-lock.json` (SQ-7). `backends` is only `["sqlite"]`, `rules` has SQ-7, and `store.lock_wait_milliseconds` is specified. `arguments` is an empty object, there is no `store`, and the expectation is only `result = success`. There is only one lock for the whole file, not per store.

- **`holdWriteLock`**: The runner opens, on the same file, a connection separate from the store's connection, takes the write lock with BEGIN IMMEDIATE, and keeps holding it.
- **`releaseWriteLock`**: Releases the held lock (closes the other connection's transaction by ROLLBACK or the like).
- An append while the lock is held fails, after waiting beyond `lock_wait_milliseconds`, with the `storage` category and not an optimistic lock, and nothing is confirmed. After the lock is released, the same append succeeds and can be read again.
- A scenario that releases a lock that is not held, a scenario that takes a lock already held again, a scenario that ends without releasing the lock, and a scenario that has no append expecting a storage error while the lock is held are rejected as errors in the data. Using this operation in scenarios where `backends` is not only `["sqlite"]` is also rejected.

### Retrying after an abort (Spanner)

The `transaction-aborted` fault is used only by the scenarios of `spanner/commit.json` (SPN-7). `backends` is only `["spanner"]`, `rules` has SPN-7, and `store.transaction_retry_limit` is specified. `phase` is `commit`, `injection` is `replace-request`, `repeat` is `mode = count`, and `repeat.count` is the number of times the abort is returned. It confirms re-execution with the same envelope and the same seq_nr when the SDK receives the abort and re-executes the transaction.

- If the number of aborts is at most `transaction_retry_limit`, the append succeeds, and the same envelope can be read as exactly one item without being renumbered.
- If the number of aborts exceeds the limit, it becomes an error of the storage category, and nothing is confirmed. Resending the same append succeeds.
- Using this kind of fault in scenarios where `backends` is not only `["spanner"]` is rejected as an error in the data.

### Bigtable write-out and the envelope limit

The stages `journal-write-previous` and `journal-write-tail` are used only by the scenarios of `bigtable/journal-write.json` (BT-7). `backends` is only `["bigtable"]`, `rules` has BT-7, and they are injected with `kind = storage-error` and `injection = replace-request`.

- **`journal-write-previous`**: The process of writing the fetched previous event to the journal before the conditional update of the head. It does not exist for the first append, which has no head, so injecting into that append is rejected as an error in the data. The failed append becomes an error of the storage category, the head does not advance, and a read returns the events up to then. Resending the same append succeeds.
- **`journal-write-tail`**: The process of writing the new tail event to the journal after the conditional update has succeeded. Even if it fails, the append succeeds, and the failure is notified as `journal-write-failure` in `observe.notifications`. A read returns up to that event. Even after the next append, all events can be read without gaps.
- A lost response of the conditional update is represented by `replace-response` of `commit`. It becomes an error of the storage category, and resending the same envelope results in an optimistic lock.
- The row "after the previous event's write-out, the new conditional update does not hold" requires interruption by another writer, so it is not included in the scenarios.

`bigtable/envelope-limit.json` (BT-16) confirms that an append of an envelope exceeding `store.envelope_limit_bytes` is rejected before writing as a contract violation of rule BT-16, and nothing is confirmed. Whether the limit is exceeded is judged by the sum (the lower bound of the envelope size) of the fixed part (27 bytes for an event, 17 bytes for a snapshot), the byte counts of aid and manifest, and the byte count of the payload as whitespace-free JSON. So that the result does not change due to differences in each language's serialization, the data creates payloads that greatly exceed the limit with `generators`.

### Operation results

| Kind of `expect` | Meaning |
|:--|:--|
| `result = success` | The write or creation succeeds. A specific return value is not required |
| `result = none` | The aggregate head does not exist, and "none" is returned |
| `result = snapshot` | Returns the pair of `head_seq_nr` and the envelope of `snapshot` (null means none) |
| `result = events` | Returns all the envelopes that `events` references, in that order |
| `error` | Becomes a failure satisfying the specified category and message conditions |

Returned events are compared not only by payload but by the whole envelope of aggregate_id, seq_nr, occurred_at, manifest, and payload. For the latest snapshot, the envelope and the head's number are compared separately. The head's number is not embedded in the fixture snapshot.

### Comparing payloads and aggregate state

The payload and `snapshot.aggregate` are arbitrary JSON values. The runner compares JSON values serialized and restored with the default JSON serializer. The order of object keys and JSON whitespace are ignored, while the order of arrays and the values of null, booleans, strings, and numbers are preserved. Booleans and numbers are not treated as identical. No Unicode normalization is applied to strings. Numbers are compared as values on JSON, and a difference in notation between `1` and `1.0` is not required.

Metadata must not be added to the payload. An attribute in the payload that resembles `seq_nr` or manifest is also treated as is, as a domain value. A case must not be made a failure merely because the byte sequence of a string or the key order differs. A large single string is specified with `generators`. The runner passes the JSON value, after finishing generation, to the library as a normal payload, manifest, or aggregate state.

Each element of `generators` has a `target` that is a JSON Pointer rooted at the case, a `character` representing one Unicode character, and a total UTF-8 byte count `byte_length`. As an example, `{"target":"/fixtures/events/e1/payload","character":"x","byte_length":420000}` replaces an empty-string payload with 420000 x's. The target is limited to empty strings that already exist in the fixtures' events and snapshots, and each pointer is specified only once. A byte count not divisible by the UTF-8 width of the character is an error in the data. It can also be specified on object attributes and array elements, and `~0` and `~1` of the pointer are decoded. The Schema is checked on the JSON before expansion, and operations are run with the value after expansion. The reference implementation is `materialize` in `tools/conformance/data.py`.

D-7's 400KB and DY-11's 1MB are DynamoDB's binary units. The item limit is 409600 bytes, and the read page limit is 1048576 bytes ([AWS's explanation of the limits](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html)). `dynamodb-item-size-head-overhead` is a case where the journal fits within the limit but exceeds the limit with the addition of the head's type_name. The head is at least 410046 bytes from the values of payload, aid, and type_name alone. This is a lower bound before counting attribute names and containers, and it does not expect strict boundary rounding ([AWS's explanation of item size](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/CapacityUnitCalculations.html)).

### Error mapping

| Category in the data | Category in the specification |
|:--|:--|
| `optimistic-lock` | Optimistic lock |
| `contract-violation` | Contract violation |
| `serialization` | Serialization |
| `configuration` | Configuration |
| `storage` | Storage |

Map the implementation's types and distinguishable codes to these 5 categories. The category must not be guessed from the string message alone. `error.rule` is the required rule number of a contract violation. `message.must_contain` and `must_not_contain` are necessary conditions on substrings of the message, and in E-3 cases the message includes the violated rule number and the seq_nr that was about to be appended. In W-9 it also includes the differing snapshot number. The head number is not made a required value for contract violations.

So that the message check does not pass by accident through part of a rule number or aid, the aid value is in principle `Order-9`, and skipped numbers are 7 or 42. The validator rejects a must_contain value if it is a substring of the same scenario's aid or error rule number, except for elements that require the whole rule number or aid. It also rejects an empty string.

`dynamodb-item-size-*` expects only the category `contract-violation`. D-7 is the decision number for exceeding the size and is not a required rule number, so `error.rule` and message necessary conditions are not attached. An error expectation without `message` compares only the category.

For optimistic locks, the aid and the number that was about to be appended are checked in the message, and the head number is not required. Test sentinels imitating raw SDK error text, connection strings, and credentials are rejected with `must_not_contain`. Without fixing the wording, a method to discriminate all the data values contained in a message cannot be defined, so v1 does not have `context_only`. These message conditions check the necessary conditions of E-2, and do not automatically prove that there is no arbitrary additional information at all.

## Injection of faults and clocks

`faults` is a declaration within a scenario. `operation` is an integer, where 0 is the creation of the store and 1 and above are 1-based operation numbers. `phase` corresponds to the following runner hooks. If an operation has multiple faults, all the faults of different phases are registered. Faults of the same phase are consumed in array order. If a registered fault does not fire, that scenario is a failure, and an inability to inject is reported as unverified.

| Phase | Where it is injected |
|:--|:--|
| `serialize-event` / `serialize-snapshot` | Serialization of the payload / aggregate state |
| `deserialize-event` / `deserialize-snapshot` | Restoration from the binary that was read |
| `commit` | The write request: TransactWriteItems in DynamoDB, COMMIT in SQLite, the commit of the read-write transaction in Spanner, and the head's conditional update (CheckAndMutateRow) in Bigtable |
| `journal-write-previous` | In Bigtable, the process of writing the previous event to the journal before advancing the head (scenarios of `bigtable` only) |
| `journal-write-tail` | In Bigtable, the process of writing the new tail event to the journal after the conditional update succeeds (scenarios of `bigtable` only) |
| `read-events` / `read-snapshot` | The storage response of each read |
| `retention-query` | The history read that selects the retention targets |
| `retention-delete` / `retention-mark` | Deletion / marking of excess history |
| `configuration-read` / `configuration-create` | Check of / conditional creation of the configuration item |

`kind = serialization-error` makes the corresponding phase of the serializer fail. It is not expected that the default JSON serializer fails naturally on normal JSON. `transaction-aborted` is a fault in which a Spanner commit ends with a transaction abort (ABORTED) (see "Retrying after an abort (Spanner)" above). `storage-error` returns the final failure of that phase of the storage or retention hook. When `details.scope = final-retention-failure`, the whole retention fails after candidate selection and before deletion is performed. The response plan of the common scenarios' `retention-query` (`history_pages` and the like, which lean toward the shape of DynamoDB communication) is mapped to the logical history hook in memory, `sqlite`, `spanner`, and `bigtable`, and to the SDK hook in DynamoDB.

For all faults, `injection` is specified to distinguish whether there are side effects.

| Specification | Request and side effects |
|:--|:--|
| `replace-request` | Does not call the target process or request, and returns the injected failure or response. A write confirms nothing |
| `replace-response` | After sending the target process or request, replaces the response passed to the library. The side effects of the request that was sent remain |

The same distinction applies to the serializer. Except for the lost responses (`replace-response`) of `commit` in Spanner and Bigtable, write failures and retention failures are `replace-request`, so changes of that request are not confirmed. Only the creation race with `install_items` confirms an item that another runner wrote first. BatchWriteItem's `unprocessed_first_n` is also `replace-request`, and the runner actually processes only the request excluding the items declared unprocessed, and assembles the response.

`kind = sdk-error` disables the SDK's own automatic retries and returns the specified failure to the library. The SDK exception is assembled from `details.code` and `cancellation_reasons`. For scenarios where the response is lost after the request is confirmed, such as a communication failure after sending, write `replace-response`. For a lost response of `commit`, the reference model treats the write as confirmed, and the library receives a storage error whose success or failure is unknown (SPN-8, BT-7). Even if a confirmed append is returned as a failure, resending the same envelope results in an optimistic lock by W-7. Because the confirmed state after a failed response of retention deletion or marking is not determined by the specification, the reference model does not guess, and skips that operation and the later state-dependent operations. `TransactionCanceledException` does not confirm the request and is injected with `replace-request`.

`cancellation_reasons` has one element for each item of the transaction. The names of write targets are, in order, `journal`, `head`, `current-snapshot`, and `history-snapshot`, listing only the actions that exist. For configuration creation, `configuration:journal`, `configuration:snapshot`, and `configuration:head` are listed. The code of an item that did not fail is the string `None`. The runner matches the target names against the actions in the actual request, and rearranges the SDK's CancellationReasons into the order of the actual actions. This array order is not enforced as the library's request order.

The head's `ConditionalCheckFailed` element has `old_head_seq_nr`, and null means that no old item is returned. The old item at the time of this failure is used for D-5's classification. A condition failure of the journal is W-7, and a `TransactionConflict` of any item is D-6's optimistic lock. Throttling other than the head's is also treated as a storage error.

`repeat` is always an object, and `{"mode":"count","count":1}` specifies the number of times it is applied to the target phase. `{"mode":"until-operation-finishes"}` makes target requests within the specified operation fail, including retries. It is not carried over to the next operation. `times` is not used.

`kind = sdk-response` uses the following response plans.

| Attribute of `details` | Response plan |
|:--|:--|
| `responses` and `unprocessed_keys` | BatchGetItem's processed items and unprocessed keys. `seed-config` / `stored-head` are the items stored in that scenario |
| `history_pages` | Returns the page sequence of history seq_nr carried in the GSI response as is. The runner does not automatically add the history just written. LastEvaluatedKey and the next ExclusiveStartKey are matched for each page |
| `omit_just_written_history` | Defaults to false. If true, confirms that history_pages does not contain the number just written. Even if false, history is not added automatically. Adding to candidates and deduplication are done by the library |
| `unprocessed_first_n` | Returns the first n deletion requests that BatchWriteItem received as UnprocessedItems, and actually processes the rest |

A response plan starts with one application to the target phase, and continues until the whole page sequence has been returned. For a partial response of BatchGetItem, only the first specified response is replaced, and after that actual responses to the unprocessed keys are returned. When replacing a response, keys that were not sent must not be returned. The history `history_pages` uses the scenario's stored history. A combination of `omit_just_written_history = true` and a page sequence containing that number is invalid. Response plans are meant to avoid waiting for the GSI to be reflected. The physical results of deletion, TTL updates, and writes are actually reflected and inspected.

`kind = read-interleave` is a specification in which the runner assembles the non-atomic response returned to the single BatchGetItem of DY-9. With `after = capture-head-before-batch`, the old head is captured with an inspection hook just before the request is sent, and the append of `interleaved_operation` is confirmed. Then the original BatchGetItem is sent to obtain the current snapshot, and with `then = replace-batch-response-head` the head in the response is replaced with the captured old head. The library is not required to make separate requests for head and snapshot. The returned pair is the old head and the new snapshot, and the injected append is reflected in the physical head. The event and snapshot in the injection also reference the same fixtures. Races in real time are not used.

`clock.epoch_seconds` is the clock at the time of marking. If an operation has `clock_epoch_seconds`, the clock is advanced before that operation. The expiry is the sum of the marking time and `store.ttl_grace_seconds`, and is not calculated from the event's occurred_at. v1 uses a clock in the year 2100, so that DynamoDB's asynchronous TTL deletion does not delete marked items during the test. The time to wait for physical deletion by the service, and the exact match of that time, are not checked.

## Observing retention, SDK requests, and attributes

`observe.history` inspects only that aggregate's history. `active` is history without a marker, `marked` is a pair of seq_nr and an expiry in epoch seconds, and `absent` is history that must not exist. The sets of active and marked are each compared by exact match. The current snapshot and the configuration item are not counted as history. In memory, the internal logical history is inspected. Tests that leave marked history as is under TTL exist only in DynamoDB.

`observe.notifications` checks whether the retention failure of the specified operation was notified through a separate path. `retention-failure` is a category that unifies observations such as callbacks and logs, and the public notification API is not fixed. `journal-write-failure` represents that, in Bigtable, the write-out of the new tail after a successful conditional update failed, and that this was likewise notified through a separate path (step 5 of BT-7). An empty array means that the operation has no failure notification. When there are multiple logs for the same final failure, they may be normalized into one failure notification.

`observe.requests` are conditions on requests of the specified API and phase. Expressions are specified with structured attribute operations and conditions. The runner parses the SDK's expressions and the bindings of attribute names and values, and compares the structures resolved to attribute names. Whitespace, the order of clauses, and the order of the AND of conditions are not compared. `update.set` is the attribute to set and its `value_binding`, `update.remove` is the attributes to remove, and `condition` represents the existence or absence of an attribute. `key_condition.all` is a set of AND conditions, and binds `operator = eq/gte` and `argument` to the operation's aggregate_id and seq_nr. The correspondence between TTL's `#ttl` and `expression_attribute_names` is made explicit as an observation of reserved-word avoidance. `expires` is Unix epoch seconds, the value referenced by ttl's `value_binding = expires`. Setting values not included in the conditions, and attributes the SDK adds automatically, are not required. `initial_batch_sizes` is the number of deletion batches excluding resends of unprocessed items, and resends are checked separately. `no_requests_in_phases` are the request phases that must not be sent in that operation, `request_count` is the exact number of times for each phase, and `minimum_request_count` is the minimum count. `classify-condition-failure-read` refers to an additional read solely for classifying a condition failure.

`observe.request_scope` checks, in DynamoDB scenarios, the range of requests the library sent during an operation (`operation` of 1 or more). `apis` is the set of permitted API names, the 6 kinds `GetItem`, `BatchGetItem`, `Query`, `TransactWriteItems`, `BatchWriteItem`, and `UpdateItem`. The API names of all requests sent during that operation must each be in this set. If there is even one `Scan`, `PutItem`, `DeleteItem`, `ExecuteStatement`, or the like, it is a failure. `aid` can only be written as `aggregate_id`, and means that the aid of the items each request reads and writes (`aid` of `Key`, `Keys`, and `Item`, and the equality condition on the partition key `aid` in the key condition of `Query`) is in every case the aid string of that operation's aggregate. A `Query` always has a key condition. In all of the 3 tables and the GSI, the partition key is `aid`. The creation of the store (`operation` of 0) is out of scope and cannot be placed in `initialization`. The scenarios that use this observation are the cases of DY-19. The reference model cannot measure requests, so it leaves this observation to the runner.

The elements of `requests` are matched to actual separate requests in array order. When multiple elements of the same API and phase are placed, it must not be judged that one request satisfied multiple elements. The conditions of paging, re-requests of unprocessed keys, and splitting of deletion batches are checked against the whole sequence of requests of that phase.

`observe.items` and `seed.items` write DynamoDB attributes in the following form.

- `table` is the mapping to the configured table names of journal, snapshot, and head.
- `attributes` is the mapping from attribute names to DynamoDB's S, N, B, L, and M, and the attribute set of the item is compared by exact match. Attributes without a definition, the current item's ttl, the marked history's active_history_seq_nr, and the configuration item's GSI attributes are not allowed.
- N in `values` is a decimal string. It is compared as an integer with the actual N. The attribute set and types of an M inside an L are compared with `nested_attributes`. The number of elements of `events` is 1.
- `binary_json` is the decoded result of B. A path such as `events[0].payload` can also be specified. It is compared by the decoded JSON value, and the appearance of the binary is not fixed.
- `generated-store-id` of `bindings` binds the first actual store_id, and checks that the value is the same in the 3 items. The specific value of a random identifier is not expected.

When seeding an item, assemble the item by adding to values the B of the paths of binary_json and the values of bindings. At observation, compare the paths specified in binary_json and bindings separately, and compare the values excluding those paths with values. Do not write the payload binary redundantly in the head's values.events. The checks of the attribute set, types, and list counts are performed on the whole actual item before exclusion.

`dynamodb/layout.json` is a reference table of the layout. The runner checks the 3 tables it actually prepared against DescribeTable and, as needed, the TTL status. The specific values of table names and GSI names are bound to the configuration values. `items` is a reference example of all kinds of items, and does not require seq_nr 3 for a first append. The method of writing values consistently is in the operation sequences of `dynamodb/item-shapes.json`, which check the same attribute sets and types as the reference examples against actual items. Streams is enabled only on head, with NEW_IMAGE. The snapshot's GSI is KEYS_ONLY, and it is checked that the current, marked history, and configuration items do not appear in it.

## Versions, hashes, and distribution

`files[].path` in manifest is a POSIX path relative to `conformance/`, and `sha256` is the SHA-256 of the file's raw bytes. Except for the manifest itself, all files including the README, the coverage table, and the Schemas are listed. The check fails on added, missing, altered, duplicated, or wrong-version files. Line endings and character encoding are also included in the hash. Line-ending conversion must not be performed at distribution. Symbolic links are not distributed.

This directory is copied with the same content into each language's repository. CI confirms that the manifest's version is the expected version, and checks the raw-byte hashes and the file set. CI must not rebuild the manifest to hide differences. Even when using an equivalent implementation, do not omit the confirmation of the exclusion of the manifest itself, the whole file set, the SHA-256, and the version. The verification tools `tools/conformance/` may be copied separately.

The steps run from the repository root are as follows. Only the Python 3 standard library is used for the manifest check.

```sh
python3 tools/conformance/manifest.py verify
# When specifying the distribution path explicitly
python3 tools/conformance/manifest.py verify --root path/to/conformance
```

To also check the Schemas, rule numbers, references, IDs, the coverage table, and the reference model, use Python 3.11 or later and uv. jsonschema and its transitive dependencies are pinned in `tools/conformance/uv.lock`.

```sh
uv run --project tools/conformance --locked python tools/conformance/validate.py
uv run --project tools/conformance --locked python -m unittest discover -s tools/conformance -p 'test_*.py'
```

Rule numbers are collected from the definitions in the local `docs/spec/core-contract.md`, `docs/spec/storage/dynamodb.md`, `docs/spec/storage/memory.md`, `docs/spec/storage/hash.md`, `docs/spec/storage/sqlite.md`, `docs/spec/storage/spanner.md`, and `docs/spec/storage/bigtable.md`.

The rule definition lines of SQLite, Spanner, and Bigtable are written in either of two forms. Each is a bold line that starts a list item, with a requirement level followed by the rule number.

| Requirement level | Japanese form | English form |
|:--|:--|:--|
| Required | `- **必須 SQ-n**` | `- **MUST SQ-n**` |
| Recommended | `- **推奨 SQ-n**` | `- **SHOULD SQ-n**` |
| Optional | `- **任意 SQ-n**` | `- **MAY SQ-n**` |

SPN-n and BT-n take the same forms (for example, `- **MUST BT-n**`). Required, recommended, and optional correspond to MUST, SHOULD, and MAY respectively. Only lines of these forms are rules; the drafts SQ-13, SPN-15, and BT-15 and the decision numbers (SQ-D, SPN-D, BT-D) are not included, in either form. Only Bigtable's decision BT-D6a is added to the coverage targets as a valid rule, because it is used in the `rules` of the envelope value table (this is the same treatment as DynamoDB's D-n). Deleted numbers and numbers merely mentioned in the body are not accepted as rules of valid cases. When the specification is placed at a different location in the copy, specify them with `--root` and `--spec-root` respectively. The latter is the directory that has core-contract.md, storage/dynamodb.md, storage/memory.md, storage/hash.md, storage/sqlite.md, storage/spanner.md, and storage/bigtable.md. The validator checks that every rule defined by these 7 documents has either a case or a reason for exclusion in `coverage.json`. A rule with neither a case nor a reason is rejected as uncovered.

At the time of writing, the rule collection in `tools/conformance/validate.py` reads only the Japanese form (`必須`, `推奨`, `任意`). A separate change makes the validator read the English definition lines (MUST, SHOULD, MAY) in addition to the original Japanese classification. This guide describes both forms so that it does not describe only the old form.

When the data has been changed, regenerate and check in the following order. The coverage table's generation mode does not check the manifest, so the last check must be run.

```sh
uv run --project tools/conformance --locked python tools/conformance/validate.py --update-coverage
python3 tools/conformance/manifest.py rebuild
uv run --project tools/conformance --locked python tools/conformance/validate.py
```

The [coverage table](../conformance/COVERAGE.md) is generated from `rules` and `coverage.json`. Excluded rules and their reasons are listed in the same table. Enumerating rules does not prove conformance; the runner must satisfy all the corresponding observations.

## Detecting contradictions in expected values with the reference model

`tools/conformance/reference_model.py` replays operation sequences with, as its state, the head number for each aggregate, the journal, the current snapshot, and the history and TTL expiry. The model does not use the expected values to update the state. It compares success, error category, rule number, all the envelopes read, retention history, and failure notifications against independently computed results. It also handles time ranges and obvious item-size excesses, failures before confirmation, cancellation reasons, history pages, and the replacement of BatchGetItem responses.

A lost response of `commit` (`replace-response`) is treated as a confirmed write, following the injection convention (the side effects of the request that was sent remain). Because the confirmed state after a failed response of a retention update or deletion is not determined by the specification, that operation and the later state-dependent operations are skipped with a reason. In the current 128 scenarios, no operation is skipped for this reason. The model also independently computes and compares with the expectation the Spanner retry limit, the Bigtable envelope limit, the meaning of Bigtable write-out failures (a failure of the write-out of the new tail does not change the success of the append), and mismatches of recorded configuration in Spanner and Bigtable. The measurement of SDK requests, physical attribute types, and the actual wording of messages are outside the model's scope, and are stated explicitly, scenario by scenario, as checks left to the runner. Item size confirms the excess of the limit only from the attribute values of the existing cases, and does not handle strict size calculation at the boundary.

The value range of T-13 is checked in integer nanoseconds. The rounding and round trip after conversion to the language's time type are the runner's checks, and the model does not decide the rounding direction. The FNV-1a 64 table is checked separately against the specification's calculation. The Bigtable envelope's fixed binary format (ADR-0008, BT-D6a) is included in the value table of values/bigtable-envelope.json, and `tools/conformance/data.py` encodes and decodes it independently of chapter 4 of the specification and checks the expected values.

The unit tests confirm that incorrect expectations are rejected, such as changing the category of `core-gap-event` to optimistic-lock, changing the expiry of `dynamodb-retention-ttl-once` to 1, advancing the head after a failure, dropping the beginning of a read, changing a write of the same seq_nr in a shared store to a success, and changing the expectation of the re-read after a rewrite to the value after the rewrite. Passing the model's checks does not mean conformance of a language implementation.

## Reporting run results

The runner reports to CI the data version, the manifest check result, the language, implementation version, and storage backend, success, failure, exclusion, and unverified for each case ID and rule number, and the failed operation number, the expected value, and the actual value. When one case has multiple rules, its result is associated with all the rules. If any point in the middle of an operation sequence differs from the expectation, the whole case must not be reported as a success from only the operations that succeeded.

Reasons are recorded for the selection of cases by differences in representational capability, optional capabilities, deleted rules, and the caller-side recommendations. The result of skipping required cases of the target storage, and the result of failing to inject a fault, must not be tallied as a success. Cases for storage backends that are out of scope need not be run. When adding a nondeterministic test such as the winner of concurrent execution, first design a declaration of a deterministic fault or order.
