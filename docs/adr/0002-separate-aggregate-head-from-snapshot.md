# 集約ヘッドをスナップショットから分離し、変更フィードの単位にする

> キーの選び方（論理シャードに揃える判断）と、シャード数・ハッシュ方式の記録と照合は、[ADR-0006](0006-key-by-aggregate-id-instead-of-logical-shards.md) で撤回した（2026-10-03）。現在は aid 文字列をキーにする。以下のキーに関する記述は、当時の判断と比較の記録である。ヘッドを分離する判断そのものは変わらない。

DynamoDB Streams が順序を保証するのは同じ項目への変更どうしだけである。ジャーナルは 1 イベント 1 項目なので、ジャーナルの Streams では同じ集約のイベントでも順序が保証されない（[modern-ddd-book#91](https://github.com/j5ik2o/modern-ddd-book/issues/91)）。集約ごとに毎回更新される項目へイベントを載せれば、その項目の Streams が集約単位で順序どおりの変更フィードになる。

問題は、その「毎回更新される項目」が現状ではスナップショットの current 項目だという点にある。current 項目は既に 2 つの役割を兼ねている。追記のたびに version を進める楽観ロックの照合点と、ときどき書かれる集約状態のキャッシュである。ここに変更フィードの運搬まで載せると、スナップショットの意味が DynamoDB の都合で崩れる。

そこで、照合点の役割を**集約ヘッド**として独立した概念にする。共通契約では次のように定める。集約ヘッドは集約ごとに 1 件あり、追記と同じ原子的な書き込みで進み（「原子的な書き込み」の意味は ADR-0005 で、観測できる確定として定め直した）、version・直近の seq_nr・その書き込みで追記したイベント封筒を持つ。スナップショットは純粋な状態キャッシュに戻り、ヘッドより古くてもよい。変更フィードはヘッド遷移の列として定義する。この定義に DynamoDB 固有の語は含まれない。「Streams は項目単位でしか順序を保証しないので、ヘッドを独立した項目にしてイベントを載せる」という部分は、DynamoDB のストレージプロファイルにだけ書く。

DynamoDB プロファイルでは、集約ヘッドを専用テーブルの独立した項目にし、Streams はこのテーブルでだけ有効にする。当時は、キーをジャーナルと同じ論理シャードの考え方に揃え、パーティションキーを `${型名}-${シャード番号}`、ソートキーを `${型名}-${値}` とした。シャード数を不変とし、テーブルに記録したシャード数とハッシュ方式をストアの生成時に照合する方針も採った。このキーと設定照合の方針は、ADR-0006 で撤回済みである。

## Considered Options

書き込み容量の比較には、スナップショット 20KB・イベント 0.5KB・10 イベントごとにスナップショット保存、という例を使う。DynamoDB の書き込みは項目サイズを 1KB 単位に切り上げ、トランザクションでは 2 倍を消費する。UpdateItem は一部の属性だけを変えても、更新前後の大きい方の項目全体で課金される（[Developer Guide: read and write operations](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html)）。

- **A. current 項目にイベントを同居させる（#91 の当初案）**: 変更が最も小さい。しかし、イベントだけの追記でもスナップショット込みの 21KB 項目を更新するため、1 追記あたり約 44 WCU かかる（10 イベントで約 440 WCU）。これは rs v3 の現状でも同じで、current 項目に version を置いていることが既にコストになっている。Streams の NEW_IMAGE にも毎回スナップショット全体が載り、400KB の上限をスナップショットとイベントで分け合う。採らない。
- **B. 集約ヘッドを専用テーブルの独立項目にする（採用）**: イベントだけの追記はジャーナル 1KB とヘッド 1KB で約 4 WCU、スナップショット保存時はさらに約 42 WCU が加わる（10 イベントで約 80 WCU）。ストリームレコードは小さく、Streams にはヘッド遷移だけが流れる。代わりにテーブルが 3 つになり、スナップショット保存時のトランザクションは 3 項目になる。
- **C. ヘッドをジャーナルテーブルに置く**: テーブルは増えない。しかしジャーナルの Streams に順序のないイベント項目と順序のあるヘッド項目が混ざり、aid / seq_nr の GSI にもヘッドが混入しないよう属性名を避ける必要がある。採らない。
- **D. ジャーナルの Streams を通知として使い、購読側で seq_nr を照合して並べ直す（modern-ddd-book ch10 の現行方式）**: ライブラリの変更が要らない。しかし購読側ごとに照合と補完のロジックが要り、補完は結果整合の GSI 読み取りに頼る。ライブラリの保証としては採らず、購読側の安全網として残す。

ヘッドのキーについては、当時、次の 2 案を比べた。

- **aggregate_id をそのままパーティションキーにする（当時は不採用、ADR-0006 で採用）**: ヘッドの位置がハッシュ関数にもシャード数にも依存しないので、作りとして安全である。しかしジャーナルと論理シャードの考え方が分かれ、event-store-adapter と pekko-persistence-dynamodb に共通する設計原則から外れるため、当時は採らなかった。
- **論理シャードのキーに揃える（当時採用、ADR-0006 で撤回）**: 設計原則は一貫する。代わりに、シャード数の変更・実装間の設定の食い違い・ハッシュ実装の誤りのどれかが起きると、既存のヘッドを見失う。ヘッドを見失うと集約が存在しないと判定され、別の位置で新規作成が通って seq_nr=1 のイベントが二重に書かれる。そこで当時は、シャード数を不変と定め、生成時の設定照合と、適合テストデータによるハッシュ実装の検証で、この経路を塞ぐ方針にした。

書き込みの分散はどちらの案でも十分である。論理シャードキーでも、ヘッドの書き込みはジャーナルと同じだけ分散する。トランザクションは別テーブル・別キーの項目をまとめて書けるので、キーの選び方はトランザクションの成立にも影響しない。

## Consequences

- 当時は、シャード数とハッシュ方式を記録する設定項目と、生成時の照合を必要とした。rs v3 も current 項目を pkey で直接読んでいるので、シャード数の変更による二重作成を防ぐためだった。ADR-0006 で論理シャードをやめたため、この記録と照合は現在の要件ではない。
- スナップショットは純粋なキャッシュになったので、なくてもよいと定めた（2026-10-02 合意、共通契約 R-3）。新規作成もスナップショットなしででき、ない場合はジャーナルの先頭からリプレイする。
- 最新スナップショットの読み取りは、ヘッドとスナップショットの 2 項目になる。BatchGetItem の強整合読み取りで 1 往復にできる。2 項目の読み取りは原子的ではないが、古い version を読んだ場合は次の書き込みの楽観ロックで検出されるので安全側に倒れる。
- ヘッドが直近の seq_nr を持つので、書き込み時に `event.seq_nr == head.seq_nr + 1` を条件式で強制する（2026-10-02 合意、共通契約 W-8）。rs v3 は「ライブラリは連続性を検証しない」と明記していたので、これは方針の転換である。変更フィードに欠番が生じなくなり、購読側の欠番検出が厳密になる。
- 連続性を強制し、1 回の書き込みで 1 イベントだけを追記するので、version と seq_nr は常に一致する。そのため version は廃止し、楽観ロックはヘッドの seq_nr で照合する（ADR-0004）。この ADR の本文で version と書いている箇所は、ADR-0004 以降は seq_nr と読み替える。
- 変更フィードの購読側には、どの転送経路でも冪等性と欠番検出を求める。DynamoDB Streams は項目単位の順序と各レコード 1 回の出現を保証するが、保持は 24 時間である。Kinesis Data Streams 経由では順序の入れ替わりと重複が起こりうる。購読側は (aggregate_id, seq_nr) で重複を捨て、欠番を見つけたらジャーナルから補う。modern-ddd-book ch10 の `applyInOrder` は、日常の経路ではなくこの安全網として残る。
- rs は v4 相当の破壊的変更になる（テーブル追加、読み書き経路の変更）。既存 rs v3 データの移行は、テーブル全体を Scan して旧項目を列挙し、新形式で書き直す方式にする。旧 pkey を計算し直す方式は、そのときのツールチェーンの `DefaultHasher` が書き込み時と同じである保証がないので避ける。
- Pekko（pekko-persistence-dynamodb）での実現は本リポジトリの範囲外で、modern-ddd-book#91 側で扱う。
