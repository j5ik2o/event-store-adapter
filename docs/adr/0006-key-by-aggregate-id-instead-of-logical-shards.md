# 論理シャードをやめ、集約 ID をキーにする

ADR-0002 では、ヘッドのキーを「aggregate_id をそのままパーティションキーにする」案と比べたうえで、pekko-persistence-dynamodb と共通の設計原則に揃えるため、ジャーナルと同じ論理シャード（`${型名}-${シャード番号}`）を採った。その後、DynamoDB 以外の保存先（Spanner・Bigtable・SQLite）でも破綻しない設計を優先すると決め、破壊的変更も許されたので、この判断を改めた。DynamoDB では 3 つのテーブルとも aid 文字列をパーティションキーにし、ジャーナルのソートキーは seq_nr（数値）にする。論理シャードとシャード数は、仕様から外す（2026-10-03 オーナーと合意、P-29）。

キーの値の種類を増やして書き込みを散らす技法（write sharding）は、値の種類が少ないキーのためのものである。集約 ID は集約ごとに違うので、そのままでいちばんよく散る。論理シャードは逆に、キーの種類を「型の数 × シャード数」に減らし、複数の集約を 1 つのキーに寄せていた。

## Considered Options

- **論理シャードを残す（ADR-0002 の判断）**: pekko-persistence-dynamodb と揃い、`型名-0`〜`型名-N` を Query すれば型ごとに集約を列挙できる。しかしパーティションキーが集約ごとに決まらないので、ジャーナルを集約単位で読むために aid の GSI（射影 ALL）が要る。GSI は強整合で読めないので、直前に確定したイベントを取りこぼし、読み直しの規則（P-26）が要った。GSI への書き込みでコストもおよそ倍になる。シャード数を変えるとヘッドを見失い、二重作成が起きる危険も残る。採らない。
- **DynamoDB だけ論理シャードを残す**: 保存先ごとに考え方が分かれ、上の欠点も DynamoDB に残る。採らない。

## Consequences

- ジャーナルを本体から強整合で Query できるので、共通契約 R-5（読み取りを始めた時点で確定していたイベントをすべて返す）をそのまま満たせる。P-26 の読み直し（DY-14）は要らなくなった。
- journal の GSI と、シャード数・ハッシュ方式の記録と照合が要らなくなった。設定項目には配置の版だけを残す。
- パーティションキーの完全一致で読むので、前方一致で別の集約の項目が混ざる問題（旧 DY-7）は起きない。
- 型ごとに集約を列挙するには、テーブルの Scan が要る。必要になったら、head テーブルに type_name の GSI を足して取り戻す。
- Spanner・Bigtable は、単調に増えるキーによるホットスポットを避けるため、aid 文字列の FNV-1a 64 を割り算せずにキーの接頭辞にする（[ハッシュ](../spec/storage/hash.md)）。シャード数を持たないので、それを変えてキーを見失うこともない。
- pekko-persistence-dynamodb とは、キーの設計が揃わなくなる。
