# DynamoDB ストレージプロファイル（草案）

[共通契約](../core-contract.md)を DynamoDB で実現する方法を定める。テーブル構成、キーの導出、属性、トランザクション、読み取り、スナップショット保持、Streams による変更フィードを扱う。

> この文書は、合意済みの事項（P-1〜P-16、ADR-0001〜0004）から導いた部分と、この文書で新たに必要になった判断 D-1〜D-9 からなる。D-1〜D-9 は 2026-10-02 に合意した（1 章）。PR #1 のレビューを受けて足した P-17〜P-22 は、2026-10-03 に合意した（[README の合意状況](../README.md#合意状況)）。「未合意」と書いた箇所は、まだ合意していない。変更するときはオーナーの合意を得る。

## 2. テーブル構成

テーブルは 3 つで、作成はライブラリの外で行う。テーブル名とインデックス名は設定で与える。

| テーブル | パーティションキー | ソートキー | GSI | Streams |
|:--|:--|:--|:--|:--|
| journal | `pkey` (S) | `skey` (S) | `(aid, seq_nr)`、射影は ALL | 無効 |
| snapshot | `pkey` (S) | `skey` (S) | `(aid, active_history_seq_nr)`、射影は KEYS_ONLY（D-3、2026-10-02 合意） | 無効 |
| head | `pkey` (S) | `skey` (S) | なし | 有効（D-4、2026-10-02 合意） |

- **必須 DY-1**: journal の GSI は、リプレイでペイロードまで読むので射影を ALL にする。
- **必須 DY-2**: snapshot テーブルでは DynamoDB の TTL を属性 `ttl` で有効にする（TTL 方式の保持を使う場合）。
- **必須 DY-3**: Streams は head テーブルでだけ有効にする。journal の Streams では集約単位の順序が保証されないので、変更フィードの供給源にしない（[ADR-0002](../../adr/0002-separate-aggregate-head-from-snapshot.md)）。

## 3. キーの導出

### 3.1 シャード番号とパーティションキー

- **必須 DY-4**: シャード番号は、集約 ID の値部分の UTF-8 バイト列に FNV-1a 64 を適用し、符号なし 64bit 整数をシャード数で割った余りとする（[ADR-0003](../../adr/0003-fix-storage-value-representations.md)）。

```
h = 0xcbf29ce484222325
for b in utf8(value):
    h = (h XOR b) * 0x100000001b3   (mod 2^64)
shard = h mod shard_count
```

- **必須 DY-5**: 3 つのテーブルとも、パーティションキーは `${型名}-${シャード番号}` とする。
- **必須 DY-6**: シャード数は 1 以上で、テーブルを作った後は変えない。

符号付き 64bit 整数しか持たない言語（Java の `long` など）では、剰余に符号なしの演算（`Long.remainderUnsigned` など）を使う。下の入出力表の `a` と `01H42K4ABWQ5V2XQEP3A48VE0Z` はハッシュ値が 2^63 以上なので、符号付きの剰余では誤った値になる。

| 値 | FNV-1a 64 | シャード数 64 | シャード数 10 |
|:--|:--|:--|:--|
| `a` | `0xaf63dc4c8601ec8c` | 12 | 6 |
| `01H42K4ABWQ5V2XQEP3A48VE0Z` | `0xadb103af5fe2a91a` | 26 | 4 |
| `01H42KBHCW1BZG504J4ZXKA2F2` | `0x0aa990285e0388ca` | 10 | 8 |
| `ユーザー` | `0x309f20171820053e` | 62 | 0 |

この表の値は Go の `hash/fnv` と Python の独自実装で一致を確かめた。適合テストデータに収録する。

### 3.2 ソートキーと aid

型名が `user-account`、値が `01H42K4ABWQ5V2XQEP3A48VE0Z`、シャード数が 64 の集約の例を示す。

| 項目 | pkey | skey |
|:--|:--|:--|
| ジャーナル（seq_nr = 3） | `user-account-26` | `user-account-01H42K4ABWQ5V2XQEP3A48VE0Z-3` |
| スナップショット（現在） | `user-account-26` | `user-account-01H42K4ABWQ5V2XQEP3A48VE0Z-0` |
| スナップショット（履歴、seq_nr = 3） | `user-account-26` | `user-account-01H42K4ABWQ5V2XQEP3A48VE0Z-3` |
| ヘッド | `user-account-26` | `user-account-01H42K4ABWQ5V2XQEP3A48VE0Z` |

aid 属性の値は、どの項目でも `user-account-01H42K4ABWQ5V2XQEP3A48VE0Z` である（共通契約 T-1）。

- **必須 DY-7**: ソートキーの前方一致で検索しない。値に `-` を含む集約があると、前方一致が別の集約の項目にも当たるからである。集約単位の検索は GSI の aid で行う。

## 4. 設定項目と照合（D-1、2026-10-02 合意）

シャード数とハッシュ方式を記録した設定項目を、journal テーブルに 1 件置く。journal テーブルは Streams を使わないので変更フィードに混ざらず、aid と seq_nr を持たないので GSI にも載らない。

| 属性 | 値 |
|:--|:--|
| pkey | `__event-store-adapter__` |
| skey | `config` |
| shard_count (N) | シャード数 |
| hash (S) | `fnv1a64` |
| layout_version (N) | この文書が定める配置の版。初版は `1` |

通常の項目の pkey は数字で終わるので、この予約値とは衝突しない。

- **必須 DY-8**: ストアを生成するとき、設定項目を `attribute_not_exists(pkey)` の条件付きで書き込む。テーブルの作成はライブラリの外だが、この書き込みはライブラリが行うので、実行時の権限に journal テーブルへの PutItem と GetItem が要る。すでにあれば読み、shard_count・hash・layout_version のどれかが自分の設定と違えば、設定エラーを返して生成を止める（共通契約 4 章）。条件付き書き込みが失敗した後のこの読み取りは、強整合読み取り（`ConsistentRead = true`）で行う。2 つの生成が競合したとき、結果整合の読み取りでは、先に書いた側の設定項目が見えないことがあるからである（P-19、2026-10-03 合意）。

## 6. 書き込み

### 6.1 トランザクションの構成

1 回の書き込みは 1 つの `TransactWriteItems` で行う（共通契約 H-1）。

| アクション | 対象 | 条件 | 含める場合 |
|:--|:--|:--|:--|
| Put | ジャーナル項目 | `attribute_not_exists(pkey)` | 常に |
| Put | ヘッド項目 | `attribute_not_exists(pkey)` | 新規作成（seq_nr = 1） |
| Update | ヘッド項目 | `seq_nr = :prev`（`:prev` は event.seq_nr − 1） | 更新（seq_nr > 1） |
| Put | 現在のスナップショット項目 | なし（ヘッドの条件で直列化される） | スナップショットを書く場合 |
| Put | 履歴のスナップショット項目 | なし | スナップショットを書き、保持件数を設定している場合 |

更新時のヘッドの Update は、`seq_nr` と `events` を上書きする。アクションは最大 4 つで、`TransactWriteItems` の上限（100 アクション、合計 4MB）に収まる。

### 6.2 失敗の分類

| 失敗 | 分類 |
|:--|:--|
| 新規作成でヘッドの条件が不成立（既に存在） | 楽観ロック（共通契約 W-3） |
| 更新でヘッドの条件が不成立 | ヘッドの seq_nr と比べて分ける（共通契約 W-8）。event.seq_nr がヘッド以下なら楽観ロック、ヘッド + 2 以上なら契約違反。判別方法は（D-5、2026-10-02 合意） |
| ジャーナルの条件が不成立 | 楽観ロック（共通契約 W-7） |
| 同じ項目への同時のトランザクション（`TransactionConflict`） | 楽観ロック（D-6、2026-10-02 合意） |
| 項目サイズの上限超過 | 契約違反。書き込み前に検査する（D-7、2026-10-02 合意） |
| スロットリング・通信の失敗・その他 | 保存先 |

D-5 の草案: ヘッドの Put / Update に `ReturnValuesOnConditionCheckFailure = ALL_OLD` を付ける。トランザクションが取り消されると、取り消し理由（`CancellationReasons` の該当要素の `Item`）にヘッドの旧項目が載るので（[API Reference: Update](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Update.html)、[CancellationReason](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_CancellationReason.html)）、その seq_nr と event.seq_nr を比べる。追加の読み取りが要らず、失敗した時点のヘッドで判別できる。更新でヘッドがなかった場合（旧項目が返らない場合）は、ヘッドの seq_nr を 0 とみなす。集約は削除されないので、seq_nr が 2 以上の追記は採番の飛びとして契約違反になる。

D-6 の草案: `TransactionConflict` は、同じ集約へ別の書き込みが同時に進んでいたことを示す。読み直して再試行すれば解消するので、楽観ロックに分類する。

D-7 の草案: DynamoDB の項目は 400KB が上限で、ヘッド項目にもイベントのペイロードが載る。上限を超える書き込みは何度試しても成功しないので、一時的な失敗と区別できるよう、書き込み前に項目サイズを見積もって契約違反を返す。

## 7. 読み取り

### 7.1 最新スナップショット

- **必須 DY-9**: ヘッド項目と現在のスナップショット項目を、1 回の `BatchGetItem` で強整合読み取りする。`UnprocessedKeys` が返れば、読み切るまで再要求する。
- **必須 DY-10**: ヘッドがなければ「なし」を返す（共通契約 R-1）。ヘッドがあれば、スナップショット封筒（なければなし）とヘッドの seq_nr の組を返す（共通契約 R-2、R-3）。

2 項目の読み取りは原子的ではない。2 つを読む間に別の書き込みが確定すると、スナップショットの seq_nr がヘッドの seq_nr を上回ることも、下回ることもある。どちらの場合も整合性は崩れない。呼び出し側が実際より古い状態から採番すれば W-8 で楽観ロックになり、新しい状態から採番すれば正しく追記できるからである。

### 7.2 イベント

- **必須 DY-11**: journal の GSI を `aid = :aid AND seq_nr >= :seq_nr` で Query し、seq_nr の昇順で返す。`LastEvaluatedKey` が返る間は続きを読み、すべて読み切ってから返す（共通契約 R-5）。
- GSI の読み取りは結果整合しか選べない。直前に確定したイベントが含まれないことがあるので、呼び出し側は共通契約 R-7 の確認を行う。

## 8. スナップショット保持（D-3、2026-10-02 合意）

保持件数 n を設定した場合だけ、履歴を書いた書き込みの確定後に保持処理を行う（共通契約 S-1〜S-4）（D-9、2026-10-02 合意）。印のない履歴は、snapshot テーブルの疎な GSI `(aid, active_history_seq_nr)` にだけ載る。現在の項目と、TTL の印を付けた履歴は載らない。

1. GSI を `aid = :aid` で Query して、印のない履歴の件数を数える（`Select = COUNT`、続きがあれば読み切る）。
2. 件数が n を超えていれば、超過分 k = 件数 − n を求め、GSI を seq_nr の昇順に k 件読む。古い履歴から選ぶことになる（共通契約 S-2）。rs v3 は現在の項目も数えていたので「件数 −（n + 1）」だったが、この GSI には現在の項目が載らないので「件数 − n」が正しい。
3. 削除方式なら、選んだ履歴を `BatchWriteItem` で削除する。1 回の要求で送れるのは 25 件までなので、25 件ずつに分けて送る（P-18、2026-10-03 合意）。`UnprocessedItems` は再送する。
4. TTL 方式なら、選んだ履歴を `SET #ttl = :expires REMOVE active_history_seq_nr` で、条件 `attribute_exists(active_history_seq_nr)` を付けて 1 件ずつ更新する。`TTL` は DynamoDB の予約語なので、属性名 `ttl` は `ExpressionAttributeNames` の別名 `#ttl` で書く。`:expires` は、印を付ける時点の Unix エポック秒に、設定で与えた猶予を足した値とする。どちらも rs v3（`delete_ttl`）と同じである（P-17、2026-10-03 合意）。GSI から外れるので、次回以降は数えられず、選び直されない（共通契約 S-3）。2 つの保持処理が同時に同じ履歴を選んでも、条件により後の更新は失敗する。この失敗は「印付け済み」として読み飛ばす。これで期限の付け直しが起きない。

保持処理が失敗しても、書き込みは成功として返し、失敗はログや通知用のコールバックで知らせる（共通契約 S-4）。

D-9 の草案の理由: 履歴が増えるのはスナップショットを伴う書き込みのときだけなので、イベントだけの書き込みの後に保持処理を行っても、数える件数は変わらない。毎回行うと、イベントだけの書き込みのたびに無駄な Query が 1 回増える。

D-3 の草案の理由: 印付け済みの履歴を除外する方法には、絞り込み条件（FilterExpression）もある。しかし絞り込みは読み取った後に捨てるだけなので、印付け済みの履歴の分まで読み取り容量を消費する。スナップショットのペイロードは大きいことが多い。キーだけを持つ疎な GSI なら、印のない履歴だけを小さく読める。この GSI が保持処理を担うので、rs v3 の snapshot テーブルにあった `(aid, seq_nr)` の GSI は不要になる。

## 9. 変更フィード

- **必須 DY-12**: head テーブルの Streams を有効にし、`StreamViewType` は `NEW_IMAGE` とする（D-4、2026-10-02 合意）。
- **必須 DY-13**: INSERT と MODIFY のレコードは、それぞれ 1 回のヘッド遷移である。`NewImage` の aid・seq_nr・events から、ヘッド遷移（共通契約 6 章）を組み立てる。ライブラリはヘッドを削除しないので、REMOVE のレコードは生じない。

DynamoDB Streams は、同じ項目への変更を変更した順に流し、各レコードを 1 回だけ流す。ヘッドは集約ごとに 1 項目で、更新は W-8 の照合で直列化されるので、同じ集約のヘッド遷移は seq_nr の順に届く。Lambda のイベントソースマッピングは、並列度（`ParallelizationFactor`）を上げても項目単位の順序を保つ。

ただし次の場合は、購読側の義務（共通契約 F-3、F-4）が実際に効いてくる。

- Streams の保持期間は 24 時間で、それ以上遅れるとレコードが消えて欠番になる。
- Kinesis Data Streams 経由で読むと、順序の入れ替わりと重複が起こりうる。

D-4 の草案の理由: ヘッド遷移の組み立てに必要なのは更新後の値だけである。`NEW_AND_OLD_IMAGES` にすると、レコードごとに直前のイベントのペイロードまで運ぶことになる。

## 10. 上限

| 上限 | 値 | 影響 |
|:--|:--|:--|
| 項目サイズ | 400KB | イベントのペイロードは、ジャーナル項目とヘッド項目の両方に載る。スナップショットのペイロードは、スナップショット項目に載る |
| トランザクション | 100 アクション、合計 4MB | 1 回の書き込みは最大 4 アクション |

## 11. rs v3 からの移行（D-8、2026-10-02 合意）

rs v3 の配置からは、全件の書き直しが要る。パーティションキーのハッシュが変わり、ヘッドのテーブルが増えるからである。

この手順の対象は、rs v3 の既定のキーの配置（`KeyResolver` を差し替えていない場合。pkey は `${型名}-${シャード番号}`、skey は `${型名}-${値}-${seq_nr}`）に限る。独自の `KeyResolver` を使っている場合は範囲外とする。手順 3 で旧 pkey・旧 skey がこの形でない項目を見つけたら、移行を止める（P-22、2026-10-03 合意）。

1. 新しい 3 つのテーブルを作り、設定項目を書く。
2. 旧テーブルへの書き込みを止める。書き直しの間に書き込みが続くと取りこぼすからである。
3. 旧 journal テーブルを Scan し、各項目を新しいキーで新 journal に書く。属性は v3 と同じ形なので、キーと aid の書式（共通契約 T-1）だけを変える。型名と値は、旧 pkey の末尾のシャード番号と、旧 skey の末尾の seq_nr を取り除いて取り出す。Scan は、書き込みを止めた後に強整合読み取り（`ConsistentRead = true`）で行い、`LastEvaluatedKey` が返らなくなるまで続ける。結果整合の読み取りや 1 ページだけの読み取りでは、イベントを取りこぼしたまま旧テーブルを捨てることになるからである（P-20、2026-10-03 合意）。
4. 集約ごとに、新 journal の最大の seq_nr を求め、ヘッド項目を作る。events には最大の seq_nr のイベントを入れる。rs v3 の current 項目の seq_nr はスナップショットの位置なので、ヘッドの seq_nr には使わない。
5. 旧 snapshot テーブルを Scan し、現在の項目と履歴を新しいキーで書く。Scan の読み方は手順 3 と同じである（P-20、2026-10-03 合意）。version 属性は捨てる。`ttl` が 0 の項目は属性を持たせず、印のない履歴には `active_history_seq_nr` を付ける。rs v3 の項目は manifest を持たないので、空文字列を入れる（共通契約 T-10 の省略時の値）（P-21、2026-10-03 合意）。
6. 新しいテーブルを使う版のライブラリで書き込みを再開する。

旧 pkey を計算し直す方式は使わない。そのときのツールチェーンの `DefaultHasher` が、書き込み時と同じ値を返す保証がないからである（[ADR-0002](../../adr/0002-separate-aggregate-head-from-snapshot.md)）。

js・java・go の旧来の契約の配置からの移行は、この文書の範囲外とする。
