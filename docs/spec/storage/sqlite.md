# SQLite ストレージプロファイル（草案）

[共通契約](../core-contract.md)を、1 つのローカルデータベースファイルのトランザクションで実現する。ヘッドを専用テーブルに置き、同じファイルを開く複数接続・同じホストの複数プロセスでも、seq_nr で追記を照合する。

> 2026-10-04 作成。1 章の SQ-D1a・SQ-D1b・SQ-D2a・SQ-D2b・SQ-D3・SQ-D4・SQ-D5a・SQ-D5b・SQ-D6・SQ-D7 は同日に合意した。草案と表示した SQ 規則の具体的な実現方法は、引き続き確認対象である。現行 rs の SQLite 実装を変更する指示ではない。実装者は 1〜5 章で配置・接続・確定を確認し、保持・購読・移行は該当する章を参照する。用語は [CONTEXT.md](../../../CONTEXT.md) に従う。

## 1. 合意した配置と能力

| 判断 | 採用した案 | 主な代案 | 状態 |
|:--|:--|:--|:--|
| SQ-D1a | 同じホストのローカルファイルを対象にし、複数接続・複数プロセスからの利用を扱う | ローカルファイルの単一接続だけに限定する、メモリデータベースにも対応する | 合意（2026-10-04） |
| SQ-D1b | ローカルファイルは WAL と synchronous=FULL を使う | rollback journal の DELETE と synchronous=EXTRA を使う、両方式を設定で選べるようにする | 合意（2026-10-04） |
| SQ-D2a | SQLite 3.51.3 以上を対象にする | 3.51.3 以上に加え、修正済みの旧版 3.44.6・3.50.7 も対象にする | 合意（2026-10-04） |
| SQ-D2b | config と任意の遷移表を含め、全テーブルを STRICT にする | 通常のテーブルを使い、型と範囲の検査をライブラリに任せる | 合意（2026-10-04） |
| SQ-D3 | 追記は BEGIN IMMEDIATE、各読み取り操作は同じ明示的な読み取りトランザクションで行う | 追記は BEGIN DEFERRED と書き込みへの移行時の競合に応じた操作全体の再実行、読み取りは同じ明示的なトランザクション | 合意（2026-10-04） |
| SQ-D4 | 古いスナップショット履歴を、追記の確定後に別トランザクションで削除する。最初の版では期限切れ方式を提供しない | 期限列と独立した遅延削除の処理を用意する | 合意（2026-10-04） |
| SQ-D5a | 任意の変更フィードを提供し、遷移表をイベントと同じトランザクションで確定する | 最初の版では変更フィードを提供しない | 合意（2026-10-04） |
| SQ-D5b | フィードの遷移表を初版では無期限に保持し、アダプタが古い遷移を削除しない | 保持期間付きの削除と、期限切れの検出・再同期を設計する | 合意（2026-10-04） |
| SQ-D6 | 未初期化の空の DB への明示的な初期化と、既存ストアを開く操作を分ける | 生成時に欠けたテーブルを自動作成 | 合意（2026-10-04） |
| SQ-D7 | 保持件数とフィード設定をストア単位でそろえ、全クライアントが照合する。変更時は追記・保守・購読を止め、変更後に再生成する | 保持件数を集約単位で管理する方式を設計する。フィード設定はストア全体でそろえる | 合意（2026-10-04） |

SQ-D1 は、対応する利用環境と保存方式を独立して確認するため、SQ-D1a・SQ-D1b に分けた。SQ-D2 は、SQLite の最低バージョンと STRICT テーブルの採用を独立して確認するため、SQ-D2a・SQ-D2b に分けた。SQ-D7 は、草案の 10 章に残していた保持・フィード設定の運用に番号を付けたものである。

SQ-D5 は、変更フィードの提供と遷移表の保持期間を独立して確認するため、SQ-D5a・SQ-D5b に分けた。

SQ-D1a の合意により、同じホストのローカルファイルを、複数接続・複数プロセスから使う場合も対象にする。書き手の照合はデータベースのトランザクションで行う。ネットワークファイルシステムとメモリだけの配置は、この版の範囲外とする。単一接続に限定する案は、別接続・別プロセスからの利用を扱えなくなるため、採用しなかった。

WAL のリセット時の既知の不具合は [3.51.3](https://www.sqlite.org/releaselog/3_51_3.html) で修正された。SQ-D2a の合意により、対応する SQLite 本体は 3.51.3 以上に限定する。[SQLite の説明](https://www.sqlite.org/wal.html#walresetbug)では、旧系列の [3.44.6](https://sqlite.org/src/info/863c171b76cd36e0)・[3.50.7](https://sqlite.org/src/info/c7facf7ac58d2cda) にも修正が取り込まれているが、個別のサポート判定と受け入れ確認を増やすため、この版では許可しなかった。

## 2. ファイル・接続・設定を照合する

- **草案・必須 SQ-1**: SQLite 3.51.3 以上を使い、全接続で `locking_mode=NORMAL`・`journal_mode=WAL`・`synchronous=FULL` を設定・確認する。shared cache は使わず、`read_uncommitted=OFF` にする。busy の待ち時間を設定で与える。ファイルは同じホストのローカルファイルシステムに置く。ネットワークファイルシステム、ATTACH で複数ファイルへ分けた配置、メモリだけの配置は範囲外とする（SP-1）。

WAL の読み手と書き手の並行動作、同じホストという前提は [WAL](https://www.sqlite.org/wal.html)、コミット時の同期は [PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) に基づく。ファイルの保存先が同期要求を守ることも前提にする。

複数接続・複数プロセスからの利用を保つため、WAL を有効にする前に locking_mode を NORMAL にする。EXCLUSIVE では接続がファイルのロックを保持し続けるためである（[PRAGMA locking_mode](https://www.sqlite.org/pragma.html#pragma_locking_mode)）。

SQ-D1b の合意により、WAL と synchronous=FULL に固定する。WAL は読み取りと書き込みを並行させられ、FULL は各コミットで WAL の同期を行う。検討した rollback journal の DELETE と synchronous=EXTRA は、コミット時に journal を削除したディレクトリも同期する方式である。両方式を選択式にする案は、モードごとの設定照合と検証が必要になるため、この版では採用しなかった。

- **必須 SQ-14**: ストアが使う全接続で `journal_mode=WAL` と `synchronous=FULL` を設定・確認する。設定と異なる値のまま読み書きを続けず、設定エラーにする。全接続で FULL を使い、同期の強さを呼び出しごとに切り替えない（2026-10-04 合意、SQ-D1b）。

- **必須 SQ-15**: ストアを開く接続から、実際に使う SQLite 本体のバージョンを取得し、3.51.3 以上であることを確認する。未満なら設定エラーにする。バージョンは各部分を整数として比較する（2026-10-04 合意、SQ-D2a）。

- **必須 SQ-2**: 生成時に config の store_id、配置の版、保持件数、フィードの有無、テーブル定義、主キーを確認する。設定項目や必要な定義の欠損・不一致は設定エラーにする。存在しないストアを、通常の「開く」操作で自動初期化しない。初期化は未初期化の空の DB だけを対象とした明示的な操作とし、DDL と設定の INSERT を 1 つのトランザクションで行う（2026-10-04 合意、SQ-D6）。照合対象の具体的な保存形式・フィールドは、この草案の案である。

SQ-D6 の合意により、明示的な初期化と、既存ストアを開く操作を分ける。初期化はストアが稼働していない状態で、新規のファイルか、アプリケーション用のテーブル・索引・ビュー・トリガーがない未初期化のデータベースだけを対象にする。SQLite のバージョンと WAL・FULL を確認した後、BEGIN IMMEDIATE の中で対象が未初期化であることを確認し、必要な DDL と config の INSERT をまとめてコミットする。

WAL の設定は、この初期化トランザクションを始める前に行う。journal_mode はトランザクション中に変更できないためである（[PRAGMA journal_mode](https://www.sqlite.org/pragma.html#pragma_journal_mode)）。通常の「開く」は既存のファイルを対象にし、設定項目や必要な定義の欠損・不一致を設定エラーにする。欠けた定義を自動で補わない。生成時に自動初期化する代案は、同時初期化の競合と、部分的な作成失敗からの回復を追加で設計する必要があるため、この版では採用しなかった。

config の `store_id` は小文字の UUID 文字列、`layout_version INTEGER` は 1 とする。`keep_snapshot_count INTEGER` は、なしなら NULL、設定する場合は正の整数とする。`retention_mode TEXT` は `delete`、`change_feed_enabled INTEGER` は 0 または 1 に限定する。設定値は SQLite の符号付き 64bit の整数に収まることも検査する。

SQ-D7 の合意により、保持件数とフィード設定をストア単位で記録し、全クライアントが自身の設定と照合する。保持件数を集約単位で指定する代案は、設定の保存先と、すべての書き手・保守処理が同じ件数を使う手順を増やす必要があるため、この版では採用しなかった。有効なストアではすべての追記で遷移を保存する（SQ-D5a）。

- **必須 SQ-19**: 保持件数とフィード設定をストア単位でそろえ、全クライアントが設定項目と照合する。不一致は設定エラーにする。設定変更は全クライアントの操作を止めて行い、変更後にストアを再生成して照合する。保持件数を変更する場合は、6 章の設定変更手順で既存履歴を整理してから設定を更新する。フィードを有効化・再有効化する場合は必要な遷移表をそろえ、7 章の復元と購読の境界をそろえる手順で購読を始める（2026-10-04 合意、SQ-D7）。

バックアップ・復元では SQLite のバックアップ手段を使い、WAL で稼働中の main ファイルだけをコピーしない。

## 3. ハッシュを使わず、aid と整数を主キーにする

SQLite はこの草案では分散配置をしないため、ハッシュの接頭辞を持たない。aid の完全一致と seq_nr の整数比較を使う（SP-2）。

| テーブル | 主キー | その他の列 |
|:--|:--|:--|
| journal | `(aid TEXT COLLATE BINARY, seq_nr INTEGER)` | `occurred_at_ns INTEGER`, `manifest TEXT`, `payload BLOB` |
| head | `aid TEXT COLLATE BINARY` | `type_name TEXT`, `seq_nr INTEGER`, `event_occurred_at_ns INTEGER`, `event_manifest TEXT`, `event_payload BLOB` |
| snapshot_current | `aid TEXT COLLATE BINARY` | `seq_nr INTEGER`, `manifest TEXT`, `payload BLOB` |
| snapshot_history | `(aid TEXT COLLATE BINARY, seq_nr INTEGER)` | `manifest TEXT`, `payload BLOB` |
| config | `singleton INTEGER`（値は 1） | `store_id TEXT`, `layout_version INTEGER`（初版は 1）, 保持・フィード設定 |
| head_transition（任意） | `transition_id INTEGER PRIMARY KEY AUTOINCREMENT` | `aid TEXT`, `seq_nr INTEGER`, `occurred_at_ns INTEGER`, `manifest TEXT`, `payload BLOB`, `UNIQUE(aid, seq_nr)` |

キーと封筒の必須列は NOT NULL、seq_nr には `CHECK(seq_nr BETWEEN 1 AND 9007199254740991)` を付ける。全テーブルを STRICT にし、INTEGER と BLOB の保存形式を保つ。STRICT の型検査は [SQLite の仕様](https://www.sqlite.org/stricttables.html) に従う。

SQ-D2b の合意により、journal・head・snapshot_current・snapshot_history・config と、有効な場合の head_transition をすべて STRICT にする。指定した型へ損失なく変換できない値を、データベースでも拒否する。STRICT でも損失のない型変換は行われるため、ライブラリでの入力検査と seq_nr の範囲の CHECK は維持する。

- **必須 SQ-16**: ストアの全テーブルを STRICT として作り、生成時に宣言を照合する。config と、有効な場合の head_transition も対象にする。通常のテーブルを混ぜた配置は設定エラーにする（2026-10-04 合意、SQ-D2b）。

- **草案・必須 SQ-3**: ライブラリは aid の型名と UTF-8 バイト長、整数の範囲を先に検査する。`occurred_at_ns` は符号付き 64bit の整数として bind し、REAL を使わない。読み取りでも整数のまま取り出す。JavaScript では BigInt などの損失のない SDK の経路を使う（T-3、T-9、T-13）。
- **草案・必須 SQ-4**: イベントとスナップショットの manifest・payload を別の列に保存する。aid はパラメータで bind し、LIKE や区切り文字による前方一致にしない。型名に `-` を含めず、文字列を正規化せずに比較する（T-1、T-7、T-11）。

SQLite の接続・ビルドの値サイズ上限は [SQLite limits](https://www.sqlite.org/limits.html) に従う。直列化の失敗は直列化エラー、保存先が返すサイズ超過や容量不足は保存先エラーにする。

## 4. 書き手の照合を BEGIN IMMEDIATE の中で行う

- **草案・必須 SQ-5**: 入力検査と直列化を済ませてから、次の処理を 1 接続の 1 トランザクションで行う。同じ接続を別の操作へ同時に渡さない。

```text
BEGIN IMMEDIATE
  ヘッドを aid の完全一致で読む
  新規作成ならヘッドの不在を確認し、更新なら W-8 を照合する
  journal にイベントを INSERT する
  head に最新 seq_nr とイベント封筒を作成・更新する
  スナップショットを伴うなら current を作成・更新する
  スナップショットを伴い、保持件数を設定していれば history に同じスナップショットを INSERT する
  フィードを利用するストアなら head_transition に同じイベントを INSERT する
COMMIT
```

ヘッドがない更新は位置 0 とみなし、2 以上の seq_nr は飛び番として契約違反にする。先行書き込みで seq_nr が既存位置以下なら楽観ロックにする。新規作成はスナップショットなしでも行える。snapshot.seq_nr と event.seq_nr の不一致は、トランザクションを始める前に契約違反にする。

BEGIN IMMEDIATE が同じファイルの書き手を直列化するので、プロセス内 Mutex がなくても、別プロセスの古い状態からの追記を照合できる。[SQLite の分離](https://www.sqlite.org/isolation.html) を前提にする。

SQ-D3 の合意により、ヘッドの照合を始める前に BEGIN IMMEDIATE で書き込みトランザクションを確保する。ロック待ちの後にヘッドを読んで照合するため、読み取りから書き込みへ移る途中で古い読み取り時点を使い続ける手順を避けられる。最新スナップショットの取得とイベントの取得は、それぞれ 5 章の明示的な読み取りトランザクションで行う。

検討した BEGIN DEFERRED は、先に読み取りを行うと、書き込みへの移行時に別接続の更新と競合して SQLITE_BUSY または SQLITE_BUSY_SNAPSHOT になり得る。そのトランザクションを終了し、同じ入力でヘッドの照合から再実行する手順が必要になるため、この版では採用しなかった（[トランザクションの仕様](https://www.sqlite.org/lang_transaction.html)）。プロセス内の Mutex だけでは別プロセスを調停できず、独立した SELECT の組では読み取り時点がずれ得るため、単独の代案にはしない。

- **必須 SQ-17**: 追記はヘッドの照合前に BEGIN IMMEDIATE を開始し、同じ接続のトランザクションで確定する。最新スナップショットの取得では head と snapshot_current、イベントの取得では head と journal を、それぞれ同じ明示的な読み取りトランザクションで読む。操作中の接続を別の操作と共有しない（2026-10-04 合意、SQ-D3）。

- **草案・必須 SQ-6**: COMMIT の成功を確定点とする。途中のエラーは ROLLBACK し、部分的な journal・head・snapshot・transition を公開しない。COMMIT のエラーではトランザクションの状態を確認して後始末し、成否を確認できなければ保存先エラーとする。確定していないと決めつけて、別の seq_nr を採番し直さない。
- **草案・必須 SQ-7**: SQLITE_BUSY・SQLITE_LOCKED と待ち時間超過は保存先エラーにする。ロック待ちを楽観ロックと混同しない。再実行は操作全体と同じ入力に対して行い、journal の INSERT だけを再送しない。

journal または新規 head の主キー重複と確認できた場合は楽観ロックにする。ほかの CHECK・NOT NULL・型・フィードの制約違反を一括して楽観ロックへ写さない。

## 5. 複数の SELECT は同じ読み取りトランザクションに入れる

- **草案・必須 SQ-8**: 最新スナップショットの取得では、BEGIN から COMMIT まで同じ接続で head と snapshot_current を読む。最初の SELECT で読み取りの時点が固定される。R-2 の組は原子的で、snapshot.seq_nr は h 以下になる（R-8）。head がなければ「なし」、head だけなら h と「スナップショットなし」を返す。
- **草案・必須 SQ-9**: イベント取得では、head と journal の読み取りを 1 つの明示的な読み取りトランザクションで行う。先に head の h を読み、`aid = :aid AND seq_nr >= :start AND seq_nr <= :h ORDER BY seq_nr` で journal を読む。`:start = max(1, seqNr)` とする。カーソルを最後まで処理し、途中で読み取りトランザクションを閉じない（R-4〜R-6）。

大量の結果をページに分けても同じ読み取り時点を使う。接続を失った場合は結果を捨てて全体を再実行する。対象範囲の欠番や必須列の欠損は保存先エラーであり、短い結果を成功として返さない。

読み取りの直後に最新の書き込みが加わっても、次の書き込みでは W-8 が現在のヘッドに対して照合される。

## 6. 履歴の削除を、追記のトランザクションから外す

SQ-D4 の合意により、保持件数を超えた古いスナップショット履歴を、追記の確定後に別のトランザクションで削除する。削除に失敗しても、確定済みの追記は成功として返す（S-4）。最初の版では期限切れ方式を提供しない。期限列と独立した遅延削除を加える代案は、印付け・件数の判定・削除処理の再実行と運用を追加で設計する必要があるため、この版では採用しなかった。

- **草案・必須 SQ-10**: スナップショットを伴う追記が確定した後、別の BEGIN IMMEDIATE で、その aid の history を seq_nr の降順に読む。新しい n 件を残し、それより古いものだけを DELETE して COMMIT する。current、head、journal、transition は削除しない。
- **必須 SQ-11**: 保持処理の busy・ディスク・SQL の失敗は通知し、追記成功を変えない。次のスナップショット書き込みか明示的な保守でやり直す（S-4）。期限切れ方式 S-3 は提供せず、TTL を要求する設定は設定エラーにする（2026-10-04 合意、SQ-D4）。

SQLite のファイル内に残る空き領域の回収と、論理的な履歴の削除は別の処理である。VACUUM を追記の成功条件に入れない。

### 保持件数の設定変更は、既存履歴を整理してから反映する

外部の管理手順で行う。通常の aid 単位の操作と異なり、全 snapshot_history の集約を列挙する。

1. ストアを使う全クライアントを止め、進行中の追記・読み取り・保持・購読が終了したことを確認する。変更前と変更先の設定、および処理の進捗を、再開に使える管理用の記録に保存する。
2. aid ごとに BEGIN IMMEDIATE で履歴を seq_nr の降順に読む。変更先が n なら新しい n 件を残し、なしなら全履歴を DELETE して COMMIT する。大きな整理は分割し、各トランザクションで選び直す。journal、head、snapshot_current、head_transition は変更しない。
3. 全集約の整理が完了してから、別の BEGIN IMMEDIATE で config の保持件数を更新して COMMIT する。全クライアントを再生成して設定を照合し、処理を再開する。

途中で失敗した場合は停止を保ち、管理用の記録にある同じ変更先で再実行する。各トランザクションの失敗はロールバックできるが、前のトランザクションで削除済みの履歴は戻せないため、ストア全体のロールバックは前提にしない。件数を増やす場合や、なしから件数を設定する場合も、削除済み・未保持の過去の履歴を補作しない。以後のスナップショット書き込みから新しい設定を適用する。これは停止中の管理手順であり、確定済みの追記の成功を変えない S-4 の保証は変わらない。

## 7. 任意の変更フィードは、遷移表を同じ確定で書く

SQ-D5a の合意により、変更フィードを任意の能力として提供する。利用するストアでは head_transition にイベント封筒を追記し、head・journal と同じトランザクションで確定する。利用しないストアでは遷移の保存を要求しない。購読側は保存した位置から読み直し、重複を除いて欠番を journal から補う（F-1〜F-4）。遷移表の保持期間は SQ-D5b で別に確認する。

- **必須 SQ-12**（利用する場合）: head_transition を追記のトランザクションに含め、イベントと同時に確定させる。sqlite3_update_hook などのプロセス内通知だけをフィードの正本にしない。プロセスの終了や再接続でも、未処理の遷移を表から読み直せるようにする（F-1、2026-10-04 合意、SQ-D5a）。
- **草案・必須 SQ-13**: 購読は `transition_id > :cursor ORDER BY transition_id LIMIT :page_size` を繰り返す。返した遷移の処理が完了してから、最後の transition_id を処理済みの購読位置にする。ID の欠番をイベントの欠番とみなさない。イベントの欠番は aid ごとの seq_nr で判定し、F-3・F-4 を行う。

transition_id は SQLite の 64bit rowid の範囲を使う。イベントの seq_nr の範囲とは別で、購読の位置は不透明な 10 進文字列などとして扱う。AUTOINCREMENT による再利用の防止は [SQLite の説明](https://www.sqlite.org/autoinc.html) に従う。

SQ-D5b の合意により、最初の版の遷移表は無期限に保持し、アダプタは古い遷移を削除しない。停止した購読は保存済み ID の次から再開する。フィードを利用するストアでは追記ごとに遷移の行が増えるため、容量の増加を見込む。保持期間付きの削除は、削除済みの境界の記録、購読の期限切れの検出、全集約の現在位置と照合する再同期を追加で設計する必要があるため、この版では採用しなかった（F-5）。

- **必須 SQ-18**（フィードを利用する場合）: 最初の版では head_transition の遷移を無期限に保持する。容量不足や ID の上限による INSERT の失敗は保存先エラーとして扱い、追記のトランザクションをロールバックする。イベントだけを確定させない（2026-10-04 合意、SQ-D5b）。

### リードモデルを作り直す場合も、復元と購読の境界をそろえる

1. 1 つの読み取りトランザクションで transition_id の最大値 m（空なら 0）と全 head の位置 h を読む。
2. その読み取り時点の journal から、各 h までのイベントを適用する。長いトランザクションを避けて別の読み取りに移るなら、控えた h を上限として適用する。
3. リードモデルの復元を完了したら m の次から購読する。F-3 の重複除去を維持する。

この初期化は無期限保持でも提供する。将来フィードの削除を加える場合は、削除済みの境界を記録して購読の期限切れを検出する方式と、F-5 の再同期をあわせて合意する。

## 8. 現行 rs からは別のファイルへ移行する

調査対象は [rs の SQLite 実装（7c6528c）](https://github.com/j5ik2o/event-store-adapter-rs/blob/7c6528c60acb787166431563f6148de5980a1667/lib/src/event_store_for_sqlite.rs)。現行は journal・snapshot の 2 テーブルで、snapshot の version を照合し、プロセス内 Mutex で接続を共有する。専用 head、STRICT の型、任意の遷移表を持つこの草案とは配置が異なる。

書き手を止めて旧ファイルを読み、新しいファイルへ移す。旧 pkey/skey や Display から型名・値を推測せず、旧 KeyResolver に対応する復元を明示する。集約ごとの seq_nr の連続性・重複・最大値を確認し、最大値の封筒から新しい head を作る。旧型名に `-` がある場合は利用者が与える対応表で置き換え、新しい aid の衝突と 1024 バイト超過を検査する。発生時刻はナノ秒の値を維持し、manifest が旧データにない場合の扱いを確認する。スナップショットの位置も検証する。

件数だけで完了とせず、aid ごとの封筒列と新しい読み取り結果を照合して切り替える。変更フィードを使う移行では、過去の全遷移を移行時に作るか、リードモデルを最大位置から初期化するかを先に決める。

## 9. 適合確認で見る事例

| 事例 | 期待する結果 | 共通規則 |
|:--|:--|:--|
| 別接続・別プロセスから同じ次の seq_nr を追記 | 1 件だけ確定。ヘッド照合に達した後続は楽観ロック、待機の上限を超えたら保存先エラー | H-2、W-8、SQ-7 |
| スナップショットなしの最初のイベント | head が存在し、snapshot はなし | W-3、R-3 |
| journal を書いた後、COMMIT 前に失敗 | 全項目と遷移がロールバックされる | H-1、F-1 |
| head と snapshot の SELECT の間に別接続が書く | 同じ読み取り時点の組を返す | R-8 |
| ロック待ち時間が尽きる | 保存先エラー。楽観ロックにしない | E-1 |
| 履歴削除が失敗する | 追記成功を保ち、次の保守で再実行 | S-4 |
| 購読が停止して再開する | ID の次から耐久的な遷移を読み直す | F-1〜F-4 |
| -1ns・64bit の両端・2^53−1 | REAL への変換なしに値を保つ | T-3、T-9、T-13 |

草案作成時は SQLite 3.53.1 の一時ファイルで SQL の試作を実行し、STRICT の配置、符号付き 64bit の両端、スナップショットなしの追記、別接続の書き込みに対する固定した読み取り時点、書き手のロック待ち、コミット前のロールバック、確定後の保持の失敗、最新 n 件の保持、遷移表と復元の境界を確認した。

この小規模な確認は、各言語のアダプタの適合を証明するものではない。fsync を守る保存先、プロセス強制終了、電源断、長時間の複数プロセス試験は未検証である。

## 10. 合意状況と実装前の確認事項

1 章の主要判断はすべて合意した。未合意の主要判断は残っていない。草案と表示した規則の具体的な実現方法は、実装前に確認する。各言語のアダプタでの検証、プロセス強制終了・電源断・長時間の複数プロセス試験も残っており、実装の適合を宣言するものではない。フィードを利用するストアでは、全書き込みで遷移を記録し、無期限保持による容量の増加を見込む。共通契約の合意済み規則は変更していない。
