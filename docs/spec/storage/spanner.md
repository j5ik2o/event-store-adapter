# Spanner ストレージプロファイル（草案）

[共通契約](../core-contract.md)を、同じ Spanner データベース内のトランザクションで実現する。ジャーナル・ヘッド・現在のスナップショット・履歴を分け、追記の確定とスナップショット保持の失敗を切り離す。

> 2026-10-04 作成。P-1〜P-40 と ADR-0001〜0006 の合意を前提とする。SPN-D1a・SPN-D1b・SPN-D2〜D7 は同日に合意した（1 章）。草案と表示した SPN 規則の具体的な実現方法は、引き続き確認対象である。実装済みの仕様ではない。実装者は 1〜5 章で配置と確定の手順を確認し、保持・購読・移行は該当する章を参照する。用語は [CONTEXT.md](../../../CONTEXT.md) に従う。

## 1. 合意した配置と能力

| 判断 | 採用した案 | 主な代案 | 状態 |
|:--|:--|:--|:--|
| SPN-D1a | 最初の版は GoogleSQL 方言だけを対象にする | PostgreSQL 方言だけを対象にする、両方を対象にする | 合意（2026-10-04） |
| SPN-D1b | 同じデータベース・同じ名前の接頭辞から 5 テーブルを導く | 個別のテーブル名を設定 | 合意（2026-10-04） |
| SPN-D2 | 追記と保持処理は SERIALIZABLE の読み書きトランザクション、復元は強整合の読み取り専用トランザクションで行う | 読み取りは強整合のまま、REPEATABLE_READ の書き込みで必要な照合・競合検出を設計する | 合意（2026-10-04） |
| SPN-D3 | 古いスナップショット履歴を即時削除する方式と、印付け後に Spanner TTL で取り除く方式を提供し、ストア単位で選ぶ | 即時削除だけを提供 | 合意（2026-10-04） |
| SPN-D4 | ヘッドだけの Change Stream を任意で提供する。取得形式は NEW_ROW | 変更フィードを提供しない | 合意（2026-10-04） |
| SPN-D5 | テーブル・設定項目・利用する Change Stream の作成は外部の初期化手順で行う。ストア生成時は照合し、欠損・不一致を設定エラーにする | ストア生成時に DDL を実行 | 合意（2026-10-04） |
| SPN-D6 | スナップショット履歴の保持件数をストア単位でそろえ、全クライアントが設定項目と照合する。設定変更は追記と保守処理を止めて行う | 保持件数を集約単位で管理する方式を設計する | 合意（2026-10-04） |
| SPN-D7 | TTL の猶予を正の整数の日数で指定する API にし、設定項目と DDL の値を照合する | Duration 型で指定し、日単位に合わない値を設定エラーにする | 合意（2026-10-04） |

SPN-D1 は、対応する SQL 方言とテーブル名の指定方法を独立して確認するため、SPN-D1a・SPN-D1b に分けた。

SPN-D6・D7 は、草案の 10 章に残していた保持件数の運用と TTL の猶予の API に番号を付けたものである。

SPN-D1a の合意により、最初の版は GoogleSQL 方言のデータベースだけを対象にする。[Spanner は GoogleSQL・PostgreSQL の両方を提供する](https://docs.cloud.google.com/spanner/docs/choose-googlesql-or-postgres) が、PostgreSQL 方言の型・DDL・エラーコードへの読み替えは、この版の範囲に含めない。対応を加える場合は、別途合意し、配置と適合確認を用意する。方言はデータベース単位でそろえる（[データベースの仕様](https://docs.cloud.google.com/spanner/docs/databases)）。

## 2. 強整合を保つ構成を前提にする

- **草案・必須 SPN-1**: 全テーブルを同じデータベースに置く。書き込みには SERIALIZABLE を明示する。読み取りには strong のタイムスタンプ境界を使い、古い時点を指定しない。Spanner のリージョン構成には追加の制限を置かない。同じデータベースのトランザクションと強整合読み取りが成立する構成を使う（共通契約 SP-1）。根拠は [トランザクション](https://cloud.google.com/spanner/docs/transactions) と [外部整合性](https://cloud.google.com/spanner/docs/true-time-external-consistency)。
- **必須 SPN-2**: ストアの生成時に、配置の版、設定項目、必要な列・主キー、保持方式を照合する。変更フィードを使うなら Change Stream の対象・取得形式・保持期間も照合する。不足や食い違いは設定エラーにする。生成時に DDL を実行したり、欠けた設定を自動で補ったりしない（2026-10-04 合意、SPN-D5）。照合対象の具体的な保存形式・フィールドは、この草案の案である。

読み取り中・稼働中の DDL 変更や、アダプタを通さないデータ変更は範囲外とする。

設定項目の `store_id` は小文字の UUID 文字列、`layout_version` は INT64 の 1 とする。`keep_snapshot_count INT64` は、なしなら NULL、設定する場合は正の整数にする。`retention_mode STRING(8)` は `delete` または `ttl`、`ttl_grace_days INT64` は TTL を使う場合だけ正の日数、それ以外は NULL とする。`change_feed_enabled BOOL` に能力の有無を記録する。設定値は列の整数の範囲に収まることも検査する。

SPN-D1b の合意により、同じデータベース・共通の接頭辞から全テーブル名を一括して導き、個別のテーブル名を受け取らない。これにより、別のストアのヘッドだけを組み合わせる設定を作れなくする。接頭辞と生成後の各テーブル名は SQL の識別子として検査し、値の条件はパラメータで渡す。

テーブル名は `<接頭辞>_<論理名>` とする。接頭辞が `esa` なら、同じデータベースの `esa_journal`・`esa_head`・`esa_snapshot_current`・`esa_snapshot_history`・`esa_config` を使う。個別の名前を指定する代案は既存の命名規則に合わせやすいが、5 テーブルが同じストアに属することを確認する方法が必要になるため、採用しなかった。

SPN-D5 の合意により、初期化は書き手がいない状態で外部手順が行う。5 テーブルと設定項目、利用する場合の Change Stream、TTL 方式の場合の行削除ポリシーをそろえてから書き手を動かす。初期化手順は DDL の完了と各テーブルが空であることを確認してから、設定項目を 1 件書く。通常のストア生成は照合だけを行い、欠けたテーブルや設定項目を自動で補わない。

SPN-D6 の合意により、スナップショット履歴の保持件数はストア単位でそろえる。config に 1 件記録し、全クライアントが自身の設定と照合する。不一致は設定エラーにする。なしなら snapshot_history に新しい履歴を残さず、設定する場合は 1 以上の整数とする（S-1）。保持件数の変更は、6 章の設定変更手順で既存履歴を整理してから外部で行い、再生成時に照合する。異なる保持件数の書き手を同時に動かさない。集約単位で指定する代案は、設定の保存先と照合手順を増やす必要があるため、この版では採用しなかった。

### SPN-D2 で合意した整合性

SPN-D2 の合意により、追記と保持処理に SERIALIZABLE を明示し、復元には strong の読み取り専用トランザクションを使う。追記をコミットした後に、別のトランザクションで保持処理を行う。保持処理の失敗は確定済みの追記に影響させない。[Spanner の隔離水準](https://docs.cloud.google.com/spanner/docs/isolation-levels)では、SERIALIZABLE は直列に実行した場合と同じ結果を保証する。競合時は中断と再実行が必要になり得る。

検討した REPEATABLE_READ は、同じデータへの書き込み競合を検出する一方、読み取った条件に依存する書き込みでは整合性が崩れる場合がある。読み取った条件と書き込みの関係を隔離水準で保つため、本版は SERIALIZABLE を採用した。将来 REPEATABLE_READ を加える場合は別途合意し、ヘッドの照合と保持対象の選択に必要な検証を設計する。性能の改善は、対象の負荷で測定して判断する。

読み取りは、ヘッドと最新スナップショット、またはヘッドとイベント列を、それぞれ同じ strong の読み取り専用トランザクションで取得する。これにより同じ時点の組を返し、読み取り開始前に確定したイベントを含める（R-5・R-8、[読み取り専用トランザクション](https://docs.cloud.google.com/spanner/docs/transactions#read-only_transactions)）。古い時点を指定する読み取りだけでは R-5 を満たせないため、単独の代案にはしない。

## 3. キーと整数を言語間でそろえる

`H(aid)` は [FNV-1a 64](hash.md) の出力を 8 バイトのビッグエンディアンにした値とする。符号付き整数への読み替えや、シャード数での剰余は使わない。

| テーブルの論理名 | 主キー | その他の列 |
|:--|:--|:--|
| journal | `(hash_prefix BYTES(8), aid STRING(1024), seq_nr INT64)` | `occurred_at_ns INT64`, `manifest STRING(MAX)`, `payload BYTES(MAX)` |
| head | `(hash_prefix BYTES(8), aid STRING(1024))` | `type_name STRING(1024)`, `seq_nr INT64`, `event_occurred_at_ns INT64`, `event_manifest STRING(MAX)`, `event_payload BYTES(MAX)` |
| snapshot_current | `(hash_prefix BYTES(8), aid STRING(1024))` | `seq_nr INT64`, `manifest STRING(MAX)`, `payload BYTES(MAX)` |
| snapshot_history | `(hash_prefix BYTES(8), aid STRING(1024), seq_nr INT64)` | `manifest STRING(MAX)`, `payload BYTES(MAX)`, `expired_at TIMESTAMP`（NULL 可） |
| config | `singleton INT64`（値は 1） | `store_id STRING(36)` と配置・保持・フィードの設定 |

- **草案・必須 SPN-3**: イベントとスナップショットの `seq_nr` は 1〜2^53−1 とする。`occurred_at_ns` は Unix エポックからの符号付き 64bit ナノ秒を保存する。TIMESTAMP 列に置き換えない。TTL の印は別の運用時刻であり、イベントの発生時刻には使わない（T-3、T-13）。
- **草案・必須 SPN-4**: aid は UTF-8 で 1024 バイト以下かをライブラリで検査する。STRING の長さ指定だけには任せない。キーは型付きの組の完全一致で比較し、aid の前方一致は使わない（SP-2）。ハッシュが衝突しても aid が異なれば別の主キーになる。
- **草案・必須 SPN-5**: SDK の INT64 は、特に JavaScript では 10 進文字列や BigInt から損失なく変換する。`occurred_at_ns` を number 経由で変換しない。payload の直列化はペイロードだけに行い、manifest と時刻は列として扱う（T-7）。

列・コミットのサイズ上限は [Spanner の上限](https://cloud.google.com/spanner/quotas) に従う。範囲・直列化の検査は書き込み前に行う。容量制限による拒否、通信障害、コミットの失敗は保存先エラーとし、SDK の生のエラーを楽観ロックのメッセージに含めない。

## 4. ヘッドの照合と全項目の書き込みを同じトランザクションに入れる

- **草案・必須 SPN-6**: イベントの検査・直列化を終えてから、次の SERIALIZABLE の読み書きトランザクションを実行する。確定点はコミットの成功である（H-1、隔離水準は SPN-D2 で合意）。

1. `(H(aid), aid)` のヘッドを読む。
2. seq_nr が 1 なら、ヘッドがない場合だけ続ける。存在すれば楽観ロックにする。2 以上なら W-8 を適用し、ヘッドがない場合は 0 とみなす。飛び番は契約違反、既存位置以下は楽観ロックにする。
3. journal にイベントを INSERT する。既存行を上書きしない。
4. head を作成・更新し、seq_nr とそのイベントの全メタデータ・payload を書く。照合対象はヘッドの seq_nr である（H-2、H-4）。
5. スナップショットを伴う場合は snapshot_current を作成・更新する。保持件数を設定していれば、同じ封筒を snapshot_history に INSERT し、`expired_at = NULL` にする。snapshot.seq_nr は event.seq_nr と一致する（W-9）。
6. コミットする。履歴を古くして削除・印付けする処理は、このトランザクションに入れない。

イベントだけの新規作成もできる。スナップショットがなければ snapshot_current に行を作らない（W-3、R-3）。

- **草案・必須 SPN-7**: SDK が ABORTED を受けてトランザクションを再実行する場合も、同じイベント封筒と同じ seq_nr でヘッドを照合する。コールバック内では外部への通知や新たな採番を行わない。同じ aid で入力の seq_nr 以上の追記が先に確定していれば、再実行時に楽観ロックとなる。再実行の上限を超えた ABORTED は保存先エラーにする。
- **草案・必須 SPN-8**: コミット応答を失った場合は、成否不明の保存先エラーとして扱う。確定していないと断定して補償書き込みを行わない。別の呼び出しで同じ seq_nr を再送した場合、既に確定していれば W-7 により楽観ロックになる。

主キー重複は、journal の `(aid, seq_nr)` または新規 head の重複と確認できた場合だけ楽観ロックへ写す。それ以外の制約・スキーマ・SDK の失敗を一括して楽観ロックにしない。

## 5. 復元は同じ強整合の読み取り時点で行う

- **草案・必須 SPN-9**: 最新スナップショットの取得では、head と snapshot_current を 1 つの strong の読み取り専用トランザクションで読む。2 つの独立した strong 読み取りを組み合わせない。これにより R-2 の組は原子的に読み取られ、snapshot.seq_nr は head.seq_nr 以下になる（R-8）。ヘッドがなければ「なし」、ヘッドだけなら「スナップショットなし」とヘッド位置を返す。
- **草案・必須 SPN-10**: イベント取得も strong の読み取り専用トランザクションで行う。最初にヘッドの h を固定し、`max(1, seqNr) <= seq_nr <= h` の journal を主キーの範囲で読み、昇順で返す。seqNr が 0 なら 1 から、h より大きければ空の列になる。

結果の分割、ストリームの途中終了、SDK のページ上限で成功を返さない。最後まで読み切り、既存集約では対象範囲の seq_nr が欠けていないことを確認する。読み取りの再開は同じ読み取り専用トランザクションで行い、それを失った場合は、ためた結果を捨てて操作全体をやり直す。範囲の欠損は保存先エラーである（R-5、R-6）。

## 6. 履歴の整理は確定の後に行う

SPN-D3 の合意により、古いスナップショット履歴の即時削除と TTL の両方式を提供する。利用する方式はストア単位でそろえる。TTL の印付けは 1 回だけ行い、印付きの履歴を保持件数に数えず、印付けの対象にも選び直さない（S-3）。物理的な削除を待つ間も、この扱いを維持する。TTL の猶予は SPN-D7 で合意した日数の API を使う。

- **草案・必須 SPN-11**: スナップショットを伴う追記が確定した後、別の SERIALIZABLE の読み書きトランザクションで、その aid の印のない履歴を seq_nr の降順に読む。新しい n 件を残し、それより古い行だけを処理する。新しい n 件の存在と候補の選択を同じトランザクションで確認する。再実行時には選び直す（隔離水準と追記からの分離は SPN-D2 で合意）。
- **草案・必須 SPN-12**: 即時削除では、対象の snapshot_history 行だけを DELETE する。snapshot_current、head、journal を削除しない。TTL 方式では、`expired_at IS NULL` の候補に `CURRENT_TIMESTAMP()` を 1 回だけ設定する。印のある行は保持件数に数えず、再び選ばない（S-3）。

TTL は snapshot_history だけに設定する。SPN-D7 の合意により、TTL を使うストアの猶予を正の整数の日数で受け取る。[GoogleSQL の行削除ポリシー](https://docs.cloud.google.com/spanner/docs/reference/standard-sql/data-definition-language#create_table)は `INTERVAL num_days DAY` で期間を指定する。例として猶予 7 日なら、次の行削除ポリシーを使う。

```sql
ROW DELETION POLICY (OLDER_THAN(expired_at, INTERVAL 7 DAY))
```

この 7 日は例であり、既定値ではない。検討した Duration 型の代案も、1 日以上で丸 1 日の整数倍という検査が必要になるため、本版は日数を直接指定する API にした。

- **必須 SPN-16**: TTL の猶予はストア単位の正の整数の日数とし、クライアントの指定値・設定項目・snapshot_history の行削除ポリシーの日数を照合する。0 以下、小数、設定列の整数の範囲に収まらない値、不一致は設定エラーにする。猶予の切り上げや切り捨てを行わない（2026-10-04 合意、SPN-D7）。

`expired_at` は、印を付けた時刻である。印のない NULL の行は TTL の対象にならない。実際の削除は期限を過ぎてからも遅れるため、印のある行をアプリケーションの保持件数に含めない。猶予を後から伸ばして、既存の印の期限を先送りする運用は範囲外とする。[Spanner TTL](https://cloud.google.com/spanner/docs/ttl) は、テーブルごとのポリシーと非同期の削除を提供する。

- **草案・必須 SPN-13**: 整理のトランザクションが失敗しても、既に確定した追記は成功として返す。別の通知経路に記録し、次のスナップショット書き込みまたは明示的な保守処理で再実行する（S-4）。大きな整理は候補を分割して行うが、各分割で新しい n 件を取り除かない条件を確認する。

### 保持件数の設定変更は、既存履歴を整理してから反映する

外部の管理手順で行う。通常の aid 単位の操作と異なり、全 snapshot_history の集約を列挙する。

1. ストアを使う全クライアントを止め、進行中の追記・読み取り・保持・購読が終了したことを確認する。変更前と変更先の設定、および処理の進捗を、再開に使える管理用の記録に保存する。
2. aid ごとに SERIALIZABLE の読み書きトランザクションで、印のない履歴を seq_nr の降順に読む。変更先が n なら新しい n 件を残し、なしなら全ての印のない履歴を対象にする。即時削除なら SPN-12 で DELETE し、TTL 方式なら `expired_at IS NULL` の候補だけに `CURRENT_TIMESTAMP()` を設定する。既に印のある行とその時刻は変更しない。大きな整理は分割し、各トランザクションで選び直す。journal、head、snapshot_current は変更しない。
3. 全集約の整理が完了してから config の保持件数を更新する。TTL 方式では、必要な印付けの完了を条件とし、物理削除を待たない。全クライアントを再生成して設定を照合し、処理を再開する。

途中で失敗した場合は停止を保ち、管理用の記録にある同じ変更先で再実行する。削除済みの行と印付け済みの行は再処理せず、期限を先送りしない。ストア全体のロールバックは前提にしない。件数を増やす場合や、なしから件数を設定する場合も、削除済み・印付け済み・未保持の過去の履歴を復活・補作しない。以後のスナップショット書き込みから新しい設定を適用する。これは停止中の管理手順であり、確定済みの追記の成功を変えない S-4 の保証は変わらない。

## 7. ヘッドの Change Stream から遷移を作る

SPN-D4 の合意により、変更フィードを任意の能力として提供する。利用するストアでは head だけの Change Stream を有効にし、NEW_ROW から確定したヘッド遷移を復元する。利用しないストアでは Change Stream の作成を要求しない。購読側は位置を保存して重複を除き、欠番を journal から補う。保持期間を超えて停止した場合は全集約の現在位置と照合して再同期する（F-3〜F-5）。

- **必須 SPN-14**（利用する場合）: head のキーと全非キー列を追跡し、`value_capture_type = 'NEW_ROW'` を使う。INSERT と UPDATE を除外しない。アダプタのトランザクションを配信対象から外す設定も使わない。DDL の完了を確認してから書き手を動かす（2026-10-04 合意、SPN-D4）。

```sql
CREATE CHANGE STREAM esa_head_changes
FOR esa_head
OPTIONS (value_capture_type = 'NEW_ROW', retention_period = '7d');
```

NEW_ROW は、更新されなかった列を含む追跡対象の行を返す。既定の OLD_AND_NEW_VALUES は変更列だけになるため、同じ payload や manifest が続いた場合の封筒復元には使わない。根拠は [取得形式](https://cloud.google.com/spanner/docs/change-streams/use-dataflow) にある。

各 mod から aid・seq_nr・イベント封筒を作る。記録の後で現在の head を読み直して代用しない。後続の書き込みで上書きされると、中間の遷移を失うからである。

- **草案・必須 SPN-15**: 分割された結果、複数の mod、子パーティションをすべて処理する。生成順はヘッドの seq_nr 順だが、複数パーティションからの受信順には依存しない。購読側は F-3・F-4 に従って重複を捨て、欠番をジャーナルから補う。

保持期間は構成から取得し、購読の位置とともに保存する。2026-10-04 に確認した [管理仕様](https://cloud.google.com/spanner/docs/change-streams/manage) では既定は 7 日、最大は 30 日である。7 日固定とみなして期限切れを判定しない。

### 保持期間を超えた購読は、現在位置との照合で再同期する

1. config の通常の strong 読み取りから、サービスが返す読み取り時刻 T を取得する。Change Stream のクエリが返す特殊な読み取り時刻を代用しない。T から新しい購読を開始し、全パーティションの以後のレコードを保持できる状態にする。クライアントの時計だけで T を決めない。
2. strong の読み取り専用トランザクションで全 head を読み、aid ごとの位置 h を控える。通常の集約操作は主キーの範囲だけを読む。この全件読み取りは再同期用である。
3. 購読側の位置から各 h までを journal で補い、F-3 の重複除去を行う。補完対象より後のイベントはこの段階の補完に混ぜない。
4. T 以後に受け取った遷移を処理する。補完との重複は捨て、パーティションの分割と後継の購読を続ける。

T より後に作られた集約は、新しい購読に作成の遷移が流れる。このため全件読み取りと並行した作成も取りこぼさない。購読の準備前に全件読み取りを始めない（F-5）。

## 8. 現行実装からは、新しい配置へ書き直す

調査対象は [js の Spanner 実装（a443ef9）](https://github.com/j5ik2o/event-store-adapter-js/blob/a443ef990e75bbbf2809c8dce49f0d42f5fa5b0d/packages/library/src/internal/spanner-event-store.ts) である。現行は journal・snapshot の配置、スナップショットの version による照合、TIMESTAMP の occurred_at を使う。この草案の専用 head とナノ秒 INT64 とは互換にならない。

移行は書き手を止めて、新しい接頭辞のテーブルへ行う。旧キーからの型名・値の復元、イベントの manifest、発生時刻の変換は旧実装の契約を確認して決める。失われたナノ秒精度を補ったことにはしない。カスタムのキー解決や、イベントに必要な情報がないデータは、自動で推測して移さない。

集約ごとの seq_nr が 1 から最大値まで欠けず、重複もないことを確認してから、新 head をその最大値と対応するイベント封筒で作る。スナップショットの seq_nr が最大値以下であることも確認する。旧型名に `-` がある場合は利用者が与える対応表で置き換え、新しい aid の衝突と 1024 バイト超過を検査する。移行後の読み戻しを照合し、Change Stream を使う場合は新しい購読とリードモデルの再構築を済ませてから切り替える。
